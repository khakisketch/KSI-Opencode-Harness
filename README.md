# KSI OpenCode Harness

> **현재 상태 (2026-10-27):** 전역 5개 역할의 위임 중심 기본값과 시각 작업 어댑터를 적용했습니다. 큰 제품·디자인 과업의 본체는 Lead에 맡기고 Build는 통합·최종 검증을 책임집니다. 실모델의 실제 위임은 관측했으나 해당 시험의 부모 최종 응답은 시간 제한으로 중단됐습니다. 새 native 렌더·디자인 품질 향상은 아직 미입증입니다. [검증 범위](docs/validation.md)

**제품을 먼저 이해하고, 스스로 설계·구현하며, 실제 화면과 동작으로 완료를 판정하는 OpenCode Native 개발 하네스입니다.**

규칙을 많이 만들기보다 제품 맥락을 정확히 전달하고, 구현 방법은 담당자에게 맡기며, 완료는 보고서나 검사 수가 아니라 실제 결과로 확인합니다.

## 처음이라면

기본 메인은 **Build**입니다. 역할 전환 명령이나 고정된 단계 없이 목표와 제약만 전달하면 됩니다.

- **기능 개발:** “현장 정사영상 비교 흐름을 구현하고 실제 화면과 테스트까지 검증해줘.”
- **화면 개선:** “이 대시보드를 현장 담당자가 업무를 파악하기 쉽게 개선해줘.”
- **분석만:** “현재 화면과 제품 정본을 대조해 UX 구조의 문제와 설계 대안을 분석해줘. 구현은 하지 마.”
- **장기 개발:** “승인된 범위의 다음 기능을 완성하고, 공유 계약과 실제 결과까지 확인해줘.”

Build가 관련 정본과 실제 코드를 확인하고 필요한 역할·모델·도구를 고릅니다. 큰·비국소·여러 부분 개발·디자인은 Lead 등에 결과 단위로 먼저 맡기는 것이 기본이며, Build는 결과를 통합·검증합니다. 해법이 열린 요청에서는 사용자 과업과 현재 문제를 짚고, 이유·주요 상충관계를 포함한 추천 방향을 먼저 제시합니다. 기존 구현을 모두 확정 요구로 취급하거나 해법 선택을 사용자에게 떠넘기지 않습니다. 범위 안의 되돌릴 수 있는 선택은 설명하고 구현·검증까지 진행하되, 제안을 범위 변경의 승인으로 간주하지 않습니다. 사용자가 디자인 규칙이나 해법을 미리 정할 필요는 없으며, 정확한 국소 수정까지 방향 발표를 요구하지는 않습니다.

**스킬도 에이전트가 선택합니다.** 일반 문장으로 요청하면 관련 스킬을 판단에 앞서 불러오고, 흐름·구조·시각·접근성 등 필요한 관점을 보완합니다. `/` 명령은 선택형 바로가기이고 `@스킬`은 직접 지정하는 방법이지, 스킬 활용의 전제 조건이 아닙니다. 중요한 제품·디자인 불확실성이 남으면 사용자의 비평 요청을 기다리지 않고 독립 확인을 고려합니다.

**UI 작업은 지침만이 아니라 도구로 연결합니다.** 명확한 시각 요청에는 설치된 공식 Impeccable을 Native가 연결하고, `visual_prepare`로 실제 제품 정본·토큰·소스를 묶습니다. 기존 Browser/Playwright 또는 실행 중인 로컬 Android 에뮬레이터의 화면을 `visual_capture`로 등록하고, `visual_review`가 원래 문제와 실제 전후 이미지를 함께 제공합니다. 자동 품질 PASS나 새 실행 엔진은 없으며, 과거 이미지·모의 입력을 새 실기 검증으로 승격하지 않습니다. [동작·한계](docs/visual-workflow.md)

**승인된 범위에서는 중간 재승인 없이 이어갑니다.** 구현·교정·검증까지 진행하고 중간 보고를 새 승인 단계로 삼지 않습니다. 일부가 막혀도 독립적인 승인 작업은 계속합니다. 질문은 목표 충돌, 권한·비용·안전·데이터 정책 변경처럼 실제 사용자 결정이 필요한 경계에서만 합니다. 분석 전용 요청이나 Plan 모드의 구현 제한은 유지합니다.

## 역할과 위임 구조

5개 운영 역할로 구성됩니다. 최대 위임 깊이는 **3**이고, 평소에는 1~2단계를 씁니다. **정해진 호출 순서는 없습니다.**

| 역할 | 맡는 일 | 기본 모델 |
| --- | --- | --- |
| **Build** | 전체 목표, 위임 중심 작업 배분, 통합, 실제 결과 판정, 최종 품질 | 세션 선택 (전역 미고정) |
| **Lead** | 배정된 기능·업무 흐름을 조사·설계·구현·검증·복구까지 완결 | Muse Contributor XHigh |
| **Plan** | 복잡한 문제, 제품·UX·기술 대안, 원인 분석과 자문 | Sol High |
| **General** | 범위가 정해진 실행·조사·구현·테스트·수리 | Muse Contributor High |
| **Explore** | 코드·외부 자료 탐색과 읽기 전용 분석 | Muse Contributor Medium |

- **Build는 큰 일을 먼저 위임합니다.** 큰·비국소·여러 부분 제품 개발·디자인은 Lead에게 결과 단위로 먼저 맡기는 것이 기본입니다(범위가 정해진 실행은 General, 읽기 전용 조사는 Explore). 조사나 마지막 리뷰만 맡기고 본체를 직접 구현하는 것은 충분한 위임이 아니며, 큰 일을 잘게 쪼개 전부 직접하는 우회도 피합니다. 정확한 국소 수정·작은 통합 수선·검증은 Build가 직접 합니다.
- **Lead는 완성 가능한 결과를 맡습니다.** 배정 범위에서 설계·구현·교정을 자율 소유하며, 작업 분해·수정 방법·필요한 자문과 위임·통합 검증까지 소유합니다. Build는 모든 세부 수정을 처방하거나 배정 중 구현을 빼앗지 않습니다.
- **Plan은 분석·자문만 합니다.** 중요한 방향이 불명확하거나 반복 수정으로도 목표를 달성하지 못하면 직접 재분석하거나 Plan을 활용합니다. 담당자는 자문의 가정과 근거를 확인해 채택한 내용을 구현·검증으로 연결하며, Plan에는 구현·승인 권한이 없습니다.
- **독립 확인은 선택입니다.** UI라면 실제 렌더 화면과 제품·시각 질문을 주고, 코드·계약만 보는 검토로 제품 수용을 대체하지 않습니다.
- **세션은 과업 단위로 씁니다.** 새 과업은 새 세션, 같은 과업의 후속 수정·재검증은 기존 담당 세션을 재개합니다. 자식의 완료는 부모 목표의 완료가 아닙니다.

## 완료를 어떻게 판정하나

**작동 검증과 제품 수용은 다릅니다.** 테스트 통과, 스크린샷 존재, 계약 일치는 증거이지 “사용자에게 좋은 제품”의 증명이 아닙니다.

Build는 완료를 선언하기 전에 원래 목표와 실제 결과를 대조합니다. UI라면 아래를 **자기 판단**으로 확인합니다. 형식 체크리스트가 아니라 판단의 예입니다.

- **첫 화면:** 제품의 목적과 다음 행동이 명확한가?
- **핵심 과업:** 사용자가 원래 하려던 일을 자연스럽게 끝낼 수 있는가?
- **시각적 위계:** 정보 구조와 화면의 중심이 사용자의 업무에 맞는가?
- **상태 조합:** 빈 상태·로딩·오류·연결 단절에서도 주요 행동이 보이고 눌릴 수 있는가? 패널·오버레이가 복구나 다음 행동을 가리지 않는가?
- **기존 기능:** 유용한 기능·데이터·권한·복구 경로를 훼손하지 않았는가?
- **반응형·접근성:** 목표 기기에서 읽고 조작할 수 있는가? 키보드 포커스·이름·대비·터치 영역이 실제로 동작하는가?

문제가 남으면 같은 담당자에게 구체적인 관찰과 함께 교정을 요청하고, 해결되지 않은 중요한 위험은 완료 보고에 명시합니다. 자식의 “완료했습니다”나 독립 검토의 “SHIP”을 그대로 최종 수용으로 삼지 않습니다.

## 모델 운영

모델과 역할은 별개의 선택입니다. Build의 모델은 세션에서 정하며 전역에 고정하지 않습니다.

| 상황 | 권장 운영 |
| --- | --- |
| 중요한 제품·다화면 UX, 최종 디자인 판단이 어려움 | **Sol High Build** |
| 방향이 확정된 장기 개발·반복 구현 | **DeepSeek Flash Max Build** + 필요할 때 Sol Plan |
| 복잡한 문제·대안·원인 분석 | **Sol High Plan**에 선택적 자문 |
| 배정된 기능 완결 | **Lead** (Muse XHigh) |
| 범위가 정해진 실행·조사 | **General** (Muse High) |
| 코드·자료 탐색 | **Explore** (Muse Medium) |

Sol High Build가 항상 DeepSeek Build보다 낫다는 결론은 아직 아닙니다. 자세한 근거와 한계는 [검증](docs/validation.md)을 보세요.

## 장기 기억 (선택)

`ai-memory` v3.2.8을 전역 보조 기억으로 연결할 수 있습니다. OpenCode·Claude Code·Codex가 같은 프로젝트의 이전 결정·실패·남은 작업을 공유합니다.

```sh
node scripts/install-ai-memory.mjs
node scripts/install-ai-memory.mjs --verify
```

- 포트 `49375`, 데이터 `~/.local/share/ai-memory`, systemd 사용자 서비스
- **allowlist:** `.ai-memory.toml`이 있는 저장소만 수집
- cloud LLM·임베딩·프로젝트 간 profile·자동 압축 비활성화
- 기억은 지시가 아니라 과거 데이터이며, 현재 코드·정본·사용자 지시가 우선

프로젝트 마커와 보안·해제 방법은 [ai-memory 안내](docs/ai-memory.md)를 참고하세요. 하네스 설정을 다시 적용한 뒤에는 `node scripts/install-ai-memory.mjs`를 다시 실행해 선택 항목을 복원하세요.

## 설치

배포 정본은 `global/`입니다. 저장소를 clone/pull하는 것만으로 전역 환경이 바뀌지 않습니다.

| 저장소 | 전역 경로 |
| --- | --- |
| `global/AGENTS.md` | `~/.config/opencode/AGENTS.md` |
| `global/opencode.jsonc` | `~/.config/opencode/opencode.jsonc` |
| `global/agents/lead.md` | `~/.config/opencode/agents/lead.md` |
| `global/commands/*.md` | `~/.config/opencode/commands/` |
| `global/plugins/ksi-visual-workflow/` | 설치기로 `~/.config/opencode/plugins/ksi-visual-workflow/`에 적용 |

기존 설정·자격증명·다른 프로젝트·세션은 보존합니다. 백업, 적용, 확인, 되돌리기는 [설치 안내](docs/installation.md)에 정리했습니다.

## 검증

```sh
# 단위·소스 계약 회귀
node --test tests/completion-guidance.test.mjs tests/capabilities.test.mjs \
  tests/session-audit.test.mjs tests/prompt-boundaries.test.mjs \
  tests/permission-probe.test.mjs tests/delegation-errors.test.mjs \
  tests/compaction-continuity.test.mjs tests/ai-memory-installer.test.mjs \
  tests/visual-workflow.test.mjs tests/visual-installer.test.mjs \
  tests/delegation-ownership.test.mjs

# 설치본 역할·모델·권한 검사 (모델 호출 없음)
node tests/agent-routing-native.mjs

# 격리 Native 위임·복구·병렬·세션 제한 통합 검사
node tests/delegation-native-integration.mjs

# 시각 도구의 격리 Native 연결·권한 검사 (합성 스킬·PNG, 로컬 scripted 모델)
node tests/visual-workflow-native.mjs

# 선택: 실제 모델의 일반 요청 위임 행동 관측 (모델 사용량 발생, 최대 5분 대기)
node tests/delegation-ownership-live.mjs
```

- **현재 통과:** 단위·설치기 회귀 **220/220**, 설치본 **146/146**, 격리 Native **362/362**, 시각 Native 연결 **16/16**. 상세 근거는 [검증](docs/validation.md)을 따릅니다.
- **Sol Build trial 1건:** 211 suites / 2,140 tests, 28개 렌더 장면, 실제 조작·axe 검증. 상세 결과와 한계는 [검증](docs/validation.md)을 보세요.
- **검사가 보장하지 않는 것:** 모델 간 일반 우위, 실제 픽셀·운영 데이터·고객/현장 인수, 장기 개발 완주. 검사는 라우팅·권한·지침 전달 메커니즘을 확인할 뿐입니다.

자세한 범위와 한계는 [검증](docs/validation.md)을 보세요.
