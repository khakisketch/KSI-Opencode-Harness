# KSI OpenCode Harness

> **상태: 전체 목표·과업 책임과 Plan 분석 자문 설명의 전역 적용·검증 완료 (2026-10-26).** 새 역할·필수 단계 없이 기존 문장을 정리했습니다. Plan은 `openai/gpt-6.1-sol#high`, 모델·모드·권한·깊이는 유지합니다. 회귀 134개·설치본 146개·격리 Native 362개가 통과했습니다. OpenSpec은 퇴역 상태를 유지하며 [실행 근거와 한계](docs/engineer-routing-validation.md)를 구분합니다. Sol Build 비교 1건은 완료됐지만 모델 우위·실제품 완주 개선은 아직 미입증입니다.

**제품을 먼저 이해하고, 스스로 설계·구현 판단을 내리며, 실제 동작하는 결과물과 화면으로 검증하도록 구성한 OpenCode Native 개발 하네스입니다.**

단순히 지침을 기계적으로 따르거나 체크리스트만 통과시키는 것을 넘어, **제품의 목적과 사용자 여정 파악 → 자율 설계·구현 → 실제 결과 검증**으로 이어지도록 역할·권한·프롬프트·검증 도구를 정의합니다. UI가 있으면 실제 렌더·조작을 확인하고, 독립 확인은 유용한 특정 질문이 있을 때만 선택합니다. 하네스의 라우팅·권한·위임 메커니즘 검사와 실제 제품의 UI/UX 완성도·장기 개발 성과는 별개입니다.

## 시작하기

기본 메인은 **Build**입니다. 정해진 명령어나 고정된 역할 전환 순서 없이, 자연어로 목표와 제약만 전달하면 됩니다.

- **기능·제품 개발 (`Build` 선택):** “현장 정사영상 비교 흐름을 구현하고 실제 화면과 테스트까지 검증해줘.”
- **UI/UX 포함 전체 과업 위임 (`Build`가 `Lead`에 배정):** “운영사 선택 및 대시보드 첫 화면을 프로답게 재설계하고 데스크톱·모바일 렌더로 검증해줘.”
- **분석·자문만 요청 (`Plan` 선택):** “실제 화면과 제품 정본을 대조해 UX 구조의 문제와 설계 대안을 분석해줘. 구현은 하지 마.”

### 사용자 상호작용 원칙
사용자가 아키텍처·역할·테스트·디자인 규칙을 일일이 지시할 필요가 없습니다.

- **자율 조사와 진행:** 목표만 주어져도(“그냥 해줘”) 프로젝트 정본과 현재 코드를 먼저 읽고 안전한 기본값을 세워 끝까지 진행합니다. 중간 마일스톤이나 하위 에이전트 완료 시점마다 “계속할까요?”라고 멈추지 않습니다.
- **질문은 권한 경계에서만:** 목표 충돌, 계약·비용·보안·데이터 정책 변경, 되돌리기 어려운 작업, 접근 권한 부재, 사용자 가치가 크게 갈리는 핵심 UI 선택에만 질문합니다(상황·선택지·추천·기본값·영향 명시).
- **시각적 선택은 말 대신 구체물로:** 레이아웃이나 흐름 선택이 필요할 때는 추상적인 텍스트 질문 대신 실제 화면 주석, 와이어프레임, 연결 흐름, 스타일 예시 중 가장 빠른 구체물을 보여주고 반응을 받습니다.
- **증상에서 바로 코드로 뛰지 않음:** 화면·제품 문제가 보고되면 실제 빌드·화면·콘솔·데이터를 먼저 관찰해 **관찰 사실과 원인 가설**을 분리하고, 깨진 사용자 과업과 해결 검증 조건을 정의한 뒤 수정합니다.

## 프로젝트 지식과 상태

전역에는 지식의 **역할·선택적 참조·갱신 원칙**만 두고, 제품 사실과 권위는 각 프로젝트가 소유합니다.

- 프로젝트 `AGENTS.md`는 짧은 제품 소개와 **기존 정본을 가리키는 지도**입니다. 과업에 관련된 정본·코드·증거를 선택하며 고정 독서 순서는 없습니다.
- 제품 목적·범위, 사용자 업무·화면 책임, 시스템·데이터 소유 경계, 검증된 현재 상태라는 **네 관점**을 찾을 수 있게 합니다. `PRODUCT/EXPERIENCE/SYSTEM/STATE` 네 파일을 만들라는 뜻이 아닙니다.
- 원장은 **현재 구현·검증 근거와 한계·남은 문제·승인된 작업 연결**만 간결하게 유지합니다. 승인된 목표와 구현 현실, 결정 이력과 현행 정본, 제품 상태와 세션 체크포인트를 구분합니다.
- 실행 담당자가 변경 사실·근거를 반환하고 Build가 공유 정본·원장을 통합합니다. 제품 사실이 바뀌지 않은 작은 수정에 원장 갱신을 붙이지 않습니다. 전역 설치로 다른 프로젝트 파일을 일괄 생성·이전하지 않습니다.

[문서 책임과 원장 예시](docs/project-knowledge.md) · [선택적 프로젝트 진입점 예시](examples/project-AGENTS.md)

## 업무가 흐르는 방식

**Build는 제품 전체 목표를, Lead는 배정된 과업의 완결을 소유합니다.** 목표와 현재 상태를
이해하고, 필요한 판단·실행을 선택하며, 실제 결과에 따라 교정·다음 작업·완료를 결정합니다.
이는 책임이 이어지는 흐름이지 순서대로 통과할 단계가 아닙니다.

- **Build의 전체 목표 책임:** 관련 정본·사용자 흐름·코드·Git 상태·실행 근거로 성공 조건을
  판단합니다. 직접 개발하거나 위임하고, 개별 과업 완료가 아니라 통합된 제품의 적합성을
  인수합니다. 승인된 상위 목표가 남아 있으면 범위 안에서 계속하며, 목표 자체를 임의로 넓히지 않습니다.
- **과업에 맞는 분담:** 끝까지 완성할 사용자 흐름이나 독립적인 시스템 기능은 Lead에
  맡길 수 있습니다. 파일·CSS·버튼처럼 기술 조각만 나누기보다 통합했을 때 의미 있는
  결과를 이루는 경계를 고릅니다. 작은 수정은 직접 하거나 General에 맡겨도 됩니다.
  병렬 작업의 공유 API·상태·파일·브라우저 소유권은 조율하되 구현 방법과 화면 배치를
  필요 이상으로 선결정하지 않습니다. Lead는 범위 안에서 조사·설계·구현·검증·복구를
  직접 수행하거나 작업자를 활용하고, 결과·근거·한계를 Build에 반환합니다.
- **독립적인 사고와 세션 활용:** 복잡한 문제 해석, 제품·UX·기술 대안, 원인 추론에는
  Sol High Plan을 선택적으로 활용합니다. Plan은 계획서 작성자나 비평 전용이 아니며
  구현·승인 권한 없는 분석 자원입니다. 새 과업은 새 하위 세션, 같은 분석의 후속 질문이나
  구현 교정은 같은 담당 세션으로 잇습니다. 범용 조사·실행에는 General, 코드·외부 자료
  탐색에는 Explore를 선택할 수 있습니다. 독립 확인이 필요하면 미참여 세션을 활용하며,
  어떤 역할도 필수 경유지가 아닙니다.
- **실제 결과로 다음 판단:** Build는 자문이나 완료 보고를 그대로 승인하지 않고 실제
  변경·테스트·실행 근거를 원래 목적과 대조합니다. UI는 초기 화면과 관련 상태·조작에서
  업무를 끝낼 수 있는지, 정보·시각적 중심이 적합한지, 기존 유용한 기능과 실패 복구를
  보존했는지 판단합니다. 문제는 관찰 사실과 함께 같은 담당자에게 교정하거나 필요한
  재조사·재배분으로 연결하고, 확인된 지속 사실은 기존 정본과 상태 원장에 반영합니다.

고정 호출 순서·필수 비평·반복 횟수·보고 양식은 없습니다. 모델과 역할은 별개의 선택입니다.
장기 개발에서 DeepSeek Build가 필요할 때 Sol Plan을 활용할 수도, 중요한 제품·다화면 UX
과업은 Build 자체를 Sol로 운영할 수도 있습니다. 어느 조합이 적합한지는 결과 품질·사용자의
추가 교정 부담·비용으로 확인하며, 완료된 비교 1건도 모델 우위의 결론이 아닙니다.

## 역할과 위임 구조

5개 운영 역할(**Build · Lead · Plan · General · Explore**)로 구성됩니다. 최대 위임 깊이는 **3**(`root 0 → 1 → 2 → 3`, 평소 1~2단계)이며, 고정 파이프라인이 아니라 작업 성격에 따라 필요한 역할만 동적으로 호출합니다. 이전 전문 4개 역할(`engineer`·`design`·`research`·`critic`) 운영 파일은 사용자 승인으로 **저장소와 전역에서 삭제됐습니다**(최종 승인 내용은 비공개 백업에만 보존, 자동 복원 없음). 전역 JSONC의 `disabled`만으로는 뒤에 발견되는 Markdown 역할을 제외하지 못했던 실험 결과에 따라 파일 자체를 제거했습니다.

| 역할 / ID | 핵심 책임과 소유 범위 | 모드 | 기본 모델 | 허용된 하위 호출 (`subagent`) |
| --- | --- | --- | --- | --- |
| **Build** (`build`) | 승인된 제품 전체 목표·작업 배분·통합·실제 결과에 따른 다음 판단·최종 품질 | `primary` | 세션 선택 (전역 미고정) | `plan`, `lead`, `general`, `explore` |
| **Plan** (`plan`) | 복잡한 문제 해석, 제품·UX·기술 대안·원인 분석과 근거 기반 자문 (선택적 활용, 구현·승인·검증 게이트 아님) | `all` | `openai/gpt-6.1-sol#high` | Native 기본값 — 분석 한정 운용 (호출 시 경계) |
| **Lead** (`lead`) | 배정된 전체 과업 소유 (조사·UX/디자인·구현·테스트·복구·완결, 직접 또는 General 활용) | `subagent` | Muse Contributor `#xhigh` | `plan`, `general`, `explore` |
| **General** (`general`) | 배정된 과업 실행 소유 — 범위 내 조사·설계·구현·테스트·수리, 스스로 검증·복귀 (자식·질문 없음) | `subagent` | Muse Contributor `#high` | 없음 (말단) |
| **Explore** (`explore`) | 코드·웹 검색과 읽기 전용 분석, 탐색 범위 보고 (편집·호출·인수 없음) | `subagent` | Muse Contributor `#medium` | 없음 (말단) |

Muse의 정확한 ID는 `opencode-go/muse-spark-1.3-contributor`입니다. Plan의 모델 선호 변경은 기존 세션에 저장된 모델을 강제로 전환하지 않습니다. 기본 프롬프트·분석 범위는 유지하며, 역할 선택과 실제 모델 선택을 구분합니다. Plan 선택만으로 shell·브라우저·네트워크의 엄격한 읽기 전용이 보장되지는 않습니다. 비변경 보호가 필요한 과업은 하위 생성 전에 기존 거부를 보존한 Native 세션 제한이나 실제 격리를 적용합니다. 모델 우위는 실제 과업에서 별도로 확인합니다.

### 역할 간 경계와 핸드오프 규칙

1. **Lead vs General (과업 소유와 실행의 분리):**
   - Lead에 배정한 전체 과업은 **`Lead`가 조사·UX/디자인·구현·테스트·복구·완결까지 소유**합니다. `Build` 직접 또는 `General` 배정도 가능하며, 복잡도·파일 수·도메인으로 `Lead` 경유를 강제하지 않습니다.
   - `General`은 배정된 과업 실행을 소유하고 범위 안에서 조사·결정·구현·검증합니다. 향후 `General`을 로컬 코딩 모델로 교체하더라도 소유권 계약은 변하지 않습니다.
2. **세션 수명주기 (같은 배정 과업에서만 재개):**
   - 새로운 과업이나 독립적인 분석은 **새 자식 세션(`sessionID` 생략)**으로 시작합니다. 새 맥락은 비평뿐 아니라 문제 해석·조사·설계·구현에도 활용할 수 있습니다.
   - **같은 배정 과업의 후속 분석·수정·보수·재검증은 기존 자식 `sessionID`를 재개(resume)**합니다. ‘1 세션 = 1 슬라이스’ 같은 고정 할당량은 KSI 정책이 아닙니다.
3. **핸드오프 맥락 (새 자식 세션 호출 시 필요):**
   - 새 자식 세션은 부모의 대화 이력을 물려받지 못하므로 필요한 목표·확정 계약·범위·완료 맥락을 전달합니다. 다음은 필요한 정보를 고르는 예시이지 고정된 5칸 보고 양식이 아닙니다:
      ① **제품·여정 맥락과 목표** (사용자·환경·앞뒤 흐름·정본 경로, 보호할 확정 계약 vs 바꿔도 되는 가설·기존 배치)
     ② **담당 범위와 보호 경계** (수정할 파일, 건드리지 말아야 할 파일·제외 범위)
     ③ **런타임·검증 환경과 증거 경로** (실행 URL/명령, 테스트 데이터, 캡처 저장 경로)
     ④ **기대 산출물과 미해결 질문**
     ⑤ **브라우저/CLI 모드** (서브에이전트에서 데스크톱 Native Browser가 `browser.disconnected`이면 재시도 없이 즉시 `playwright-cli -s=<role>-<task>` 사용)
4. **위임은 인수가 아님 (부모가 직접 확인):**
    - 부모는 자식의 **실제 diff·증거**를 직접 확인합니다. 결과물에 UI 표면이 있으면 **초기 진입·핵심 상태의 목표 기기 캡처와 조작**까지 확인합니다. 호출·캡처·검사 수만으로 과업 적합성을 인정하지 않습니다.

## 디자인·엔지니어링 실행 원칙

### 1. 프로덕트 디자인 (배정 책임에 따름 — Build 직접·General 포함)
기술적 작동과 디자인 적합성을 구분합니다. 스킬·레퍼런스는 적용 원리가 실제 구성에 반영됐는지까지 확인하며, 별도 보고서·점수표를 요구하지 않습니다. 강제 스킬 단계·순서와 CSS 전담 규칙은 두지 않으며, 과업에 맞는 렌즈를 필요할 때 로드합니다.

- **실제 제품 라우트 직접 수정:** 별도 와이어프레임만 요청받은 경우가 아니면 분리된 정적 HTML 파일(`workspace.html` 등)에 도피하지 않고 실제 제품의 라우트와 컴포넌트 트리를 직접 수정·연결합니다.
- **필요 시 로드하는 스킬 렌즈:** 과업 흐름·정보 구조에는 `designing-user-experience`(복수 화면·비교·네비게이션 재편 시 `journey`, `organize`, `wireframe`)로 **사용자가 데이터를 탐색·비교·결정하는 정보 구조와 상태 전이**부터 잡습니다. 시각 조형·문구 마감에는 `impeccable`을 필요할 때 쓰고, `ux-copy`는 **실제 사용자 문구를 검토·변경하는 과업일 때만** 씁니다. 어떤 호출도 기본 통과 조건이 아닙니다.
- **과업 기반의 레이아웃 비례와 조형 (고정 비율 강제 지양):**
  - 모든 화면에 획일적인 수치(고정 비율·고정 폭)를 강제하지 않고 **해당 화면의 핵심 사용자 과업과 데이터 성격**에서 구성을 도출합니다.
  - 공간 작업은 시각 과업을, 폼·설정·오류 해결은 해당 콘텐츠와 행동을 우선합니다. 매체 부재는 정직하게 복구하며 다른 자료·시점·출처로 몰래 대체하지 않습니다. 대안은 제품 계약에 맞는 명시적 선택으로 제공합니다.
  - 터치 영역과 읽기 전용 띠의 높이는 별개입니다. 제목·영역도 문맥 전환의 포커스 대상일 수 있으므로 필요한 키보드 포커스를 스타일 때문에 제거하지 않습니다.
- **하네스 내부 메모와 도메인 출처·상태 정보의 명확한 구분:**
  - 내부 에이전트·디버그 잡담은 제품 UI에서 제외하되, 필요한 도움말과 실제 프로토타입·시뮬레이션 고지는 보존합니다.
  - 출처·정합·검증 한계는 판단에 영향을 주는 상태를 눈에 보이게, 보충 근거는 상세로 제공합니다. 요청 접수·모의 렌더를 실제 장치 결과로 표현하지 않습니다.

### 2. 엔지니어링 및 정본 관리 (배정 책임에 따름)
- **코드 선행 대조와 범위 내 자율 재빌드:** 문서는 코드보다 늦게 갱신되므로 계획·구현 전 반드시 실제 파일과 최근 커밋(`git status`/`log`)을 대조해 이미 구현된 기능을 재작업하지 않습니다. 코드 수정 후에는 **자신이 소유한 로컬 번들·개발 서버·격리 컨테이너·승인된 로컬 APK 빌드를 자율 재빌드/재기동**하여 실제 런타임에서 검증하되, **공유 서비스·공유 컨테이너·운영 환경·미승인 실기 상태는 임의로 재시작하거나 변경하지 않습니다.**
- **원인 기반 디버깅 렌즈 (`diagnosing-bugs`, 선택):** 원인이 불분명하거나 반복되는 버그에 유용한 참고 순서(재현 신호 → 가설·이분 탐색 → 최소 수정 → 회귀 테스트 → 런타임 재검증)이며, 강제 절차가 아닙니다. 결과물의 실제 검증이 필수입니다.
- **프로젝트 정본과 간결한 원장:**
  - 각 프로젝트 `AGENTS.md`에서 관련 정본과 충돌 시 권위를 찾습니다. 상태 원장은 구현·검증 사실의 진입점이지 승인된 제품 요구사항을 바꾸는 권위가 아닙니다. 변경된 지속 사실은 소유 정본과 상태 요약에 반영하고, 기존 결정·검증 이력은 연결합니다([상세 기준](docs/project-knowledge.md)).
  - 별도 명세 프레임워크를 요구하지 않습니다. OpenSpec의 활성 루트·명령·스킬은 제거했고, 이전 명세·변경·생성물은 [퇴역 기록](docs/archive/openspec-2026-10-26/README.md)에 보존합니다. 과거의 OpenSpec 사용 조항은 현행 의무가 아닙니다.

## 검증 및 실행 감사

이 저장소는 회귀·스펙 정합성·설치본 정책·격리 Native 메커니즘을 검사합니다. 실행 감사는 별도의 **선택 진단이며 합격 게이트가 아닙니다.** 어느 검사도 모델의 디자인 판단력이나 제품 완주를 인증하지 않습니다.

```sh
# 1. 단위·소스 계약 회귀 (모델의 판단력 검사가 아님)
node --test tests/completion-guidance.test.mjs tests/capabilities.test.mjs tests/session-audit.test.mjs tests/prompt-boundaries.test.mjs tests/permission-probe.test.mjs tests/delegation-errors.test.mjs tests/compaction-continuity.test.mjs

# 2. 전역 설치본 5개 프로필 등록·모델·권한·본문·retired 제외 검사 (모델 호출 없음)
node tests/agent-routing-native.mjs

# 3. 격리 Native 서버 5프로필·깊이 3·위임·복구·병렬·세션 제한 상속 통합 검사 (로컬 fixture 모델)
node tests/delegation-native-integration.mjs

# 선택 진단: 등록 점검과 세션 흔적 관찰 — 품질/합격 판정 아님
node scripts/capabilities.mjs
node scripts/session-audit.mjs <session-json-file-or-dir>
```

- **세션 실행 이상 징후 탐지기 (`scripts/session-audit.mjs`):** 명시적으로 완료된 호출만 관찰 집계하며 미완료·실패를 분리합니다. 선택 스킬·렌더 캡처 누락은 실패로 집계하지 않습니다. 배열에 보이는 열람·편집 순서, 이미지 경로 열람과 검증 명령 패턴을 보여주지만 이미지의 관련성·검사 성공·제품 이해를 판정하지 않습니다. 누락 표시는 주입된 지침·앞선 맥락·인라인 이미지·부분 스냅샷을 고려해 수동 확인해야 합니다. 파일 제외·오류·중복 창·명시 ID/익명 스냅샷 범위를 공개하며, 파일 수를 독립 세션 수나 품질 점수로 해석하지 않습니다.
- 상세 검증 기록과 아직 미입증인 모델·렌더·실제 과업 효과: [현행 구성·적용 검증](docs/engineer-routing-validation.md) · [전체 검증 안내](docs/validation.md). [과거 OpenSpec·스킬 채택 기록](docs/openspec-and-skills.md)은 역사·출처 자료이며 현재 실행 절차가 아닙니다.
