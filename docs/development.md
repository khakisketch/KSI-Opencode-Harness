# 개발·검증 루프

이 문서는 하네스를 바꿀 때 **무엇을 먼저 확인하고, 어떤 명령으로 검증하며, 어디까지 증명되는지**를 한곳에 모읍니다. 제품 수용이나 모델 품질 평가를 대신하지 않습니다.

## 한 명령으로 확인

```sh
node scripts/verify-harness.mjs            # 기본: 오프라인 단위·설치기 회귀
node scripts/verify-harness.mjs --status   # 소스/설치본 에이전트 모델 표
node scripts/verify-harness.mjs --native   # 격리 Native 실행·위임·시각·기능 목록
node scripts/verify-harness.mjs --installed # 실제 설치본 역할·해시·catalog
node scripts/verify-harness.mjs --all      # 위 세 가지 + 상태 표
```

- `--live`는 **실제 모델 호출**이며 과금·한도를 사용합니다. 기본 실행에 포함되지 않습니다.
- 각 실행의 전체 로그는 `~/.local/share/ksi-harness-verification/<timestamp>/`에 소유자 전용으로 남습니다.
- 실패하면 마지막 20줄과 로그 경로를 보여 주고 종료 코드 1을 반환합니다.
- `--json`은 자동화용 요약을 출력합니다.

## 무엇을 검증하나

| 모드 | 확인하는 것 | 확인하지 않는 것 |
| --- | --- | --- |
| `--offline` | `tests/*.test.mjs`와 시각 외부 증거 단위 검사. 설치기·평가기·권한 경계의 합성 회귀 | 실모델 품질, 실제 제품 수용 |
| `--native` | 별도 HOME·서버·scripted 모델에서의 위임 깊이·모델 상속·Plan 제한·시각/기능 목록 연결 | 실제 모델의 자율 판단, 실기기, 실서비스 |
| `--installed` | 실제 전역 catalog의 역할·모델·권한, 관리 파일 해시, 설치기 `--verify` | 모델 호출 성공, 제품 동작 |
| `--live` | 사용자가 명시한 실모델 probe | 일반화 가능한 품질 점수 |

`--installed`는 이 Mac의 설치본을 읽습니다. 소스가 휴대용 기본값이고 설치본에 머신별 override가 있을 수 있으므로, `--status`의 `(drift)`는 **오류가 아니라 차이**입니다.

### 작업 전 Plan 자문과 병렬 개발

Plan의 Explore 호출 허용은 실행 위치에 따라 다릅니다. 독립 Root 세션으로 실행된 Plan은 Explore를 호출할 수 있고, Build의 자식으로 실행된 Plan은 깊이 1 가드에 의해 재위임이 거부됩니다. 이것은 의도된 동작이며, 자식 Plan이 조사 확장을 필요로 하면 Build가 직접 Explore를 호출합니다.

### 언제 병렬로, 언제 순차로

모든 작업을 병렬로 보내면 통합 비용이 이득을 먹습니다. 기준은 의존성과 간섭 여부입니다.

| 상황 | 권장 방식 |
| --- | --- |
| 코드베이스 탐색과 외부 자료 조사 | Explore 자식 2~3개를 병렬로 (읽기 전용이라 간섭 없음) |
| 설계 검토와 코드 분석 | Plan 자문 + Explore 조사를 병렬로, Build가 종합·결정 |
| 단일 기능의 구현 | Build 직접. 분리 이득이 분명할 때만 General 1개에 위임 |
| 서로 독립된 기능 2~3개 구현 | worktree별 독립 세션으로 병렬, Build가 메인에서 통합·검증 |
| 기존 기능 수정과 테스트 | 한 작업공간에서 순차 진행 (테스트가 수정 결과에 의존하므로) |
| 전체 제품 검증 및 통합 | Build 주도 (자식 보고를 믿지 않고 원래 과업과 대조) |

### 작업 상태 추적 (프로젝트별 Beads, opt-in)

해당 프로젝트에 `.beads/`가 있으면 Build가 작업 상태를 거기에 둡니다. 없으면 만들지 않고 파일 기반으로 진행합니다.

- 시작: `bd create`로 목표·수용 기준·핵심 참조를 적습니다. 제목만 금지.
- 인수: `bd update <id> --claim`으로 선점하고, `bd ready`로 의존성 순서대로 가져옵니다. 세션 재개 시 bead부터 읽습니다.
- 종료: `bd close --reason`으로 결과·근거를 남깁니다. 중요한 결정·재사용 지식만 `bd remember`로 남기고, 전 실행 기록을 자동 저장하지 않습니다.
- hard rule: Beads는 저장·전달 수단이며 계획 권한은 Build/Plan에 있습니다. 위임 판단·아키텍처 결정을 Beads에 맡기지 않습니다.

원칙:

- 자문은 선택입니다. 판단이 어렵거나 아키텍처 선택이 걸릴 때만 Plan에 한 번 묻고, 작은 수정에는 생략합니다. Plan은 조언만 하고 Build가 결정·실행합니다.
- 자식은 말단이라 하위 위임을 못 합니다. 조사와 구현이 모두 필요하면 처음부터 Explore와 General을 함께 붙이지, General에게 조사를 기대하지 않습니다.
- 병렬은 최대 2~3개까지. 같은 파일을 만지거나 순서가 의존적인 일은 병렬로 보내지 않습니다.
- 같은 과업의 후속 분석·수정·검증은 같은 자식 세션을 resume해서 이어가고, 새 과업은 새 자식으로 시작합니다.
- General에는 입력 자료·변경할 파일 범위·완료 기준(검사 명령과 기대 결과)을 함께 줍니다. 기준 없이 “잘 만들어줘”로 맡기지 않습니다.
- worktree는 DB·포트·브라우저·OS를 격리하지 않습니다.
- 독립 Build 세션은 형제 루트 세션으로 둡니다(자식 Build 금지). Main Build가 작업 분할·결과 수집·통합·검증을 맡고, 각 세션은 자신의 worktree에서만 일합니다. 세션 간 자동 상태 공유·완료 알림은 없으므로, 결과 수집과 실패 복구는 Main이 명시적으로 수행합니다.
- worktree 제거 전에는 미통합 커밋·수정 파일·사용 중 세션이 없는지 확인합니다. `force` 제거는 해당 worktree에 대한 명시적 사용자 확인이 있을 때만 하며, 검증되지 않은 변경의 자동 force 삭제는 하지 않습니다. worktree 생성·배정·통합·정리의 책임은 Build에 있고, 작업자는 배정된 작업공간을 벗어난 생명주기를 관리하지 않습니다. Build 지침 본문은 `global/opencode.jsonc`에 두고 설치 시 병합합니다.

모델을 바꾸려면 먼저 같은 과업을 **Build 직접 / Plan 자문 후 Build 실행 / General 분담**으로 실행해 완료율·재작업·도구 오류·비용을 비교합니다. 검증 명령 통과만으로 모델 교체를 정당화하지 않습니다.

### 구현 담당 선택과 UI 검토 기준 (2026-11-06, 2026-11-08 개정)

- Build는 개발·통합의 최종 책임자로 직접 구현과 위임을 자율적으로 선택한다. 기준은 파일 수·작업 규모가 아니라 제품 맥락(전체 이해 필요 여부)·작업 독립성(분리 구현·검증 가능 여부)·필요 역량(UX 판단 vs 일반 구현)·검증 가능성·전달 비용이다.
- 중요한 UX 불확실성이 남으면 실제 렌더와 사용자 과업을 바탕으로 검토한다. UI 판단은 Build가 소유하며, 필요하면 독립 컨텍스트의 읽기 전용 검토를 한 번 요청할 수 있다. Build는 지적의 수용 여부와 이유를 판단하고 실제 결과를 재검증한다.
- 검토에는 사용자 목표, 대상 화면·상태, 최신 렌더, 관련 레퍼런스와 누적 피드백을 전달한다. 알려진 결함을 재확인하면서 새로운 중요한 문제도 자유롭게 찾는다. 결함 위치·영향·재현·미확인을 구체적으로 남기되 식별자나 특정 보고서 형식을 의무화하지 않는다.
- 같은 작업의 반복 검토는 권한·범위가 맞는 동일 세션을 재사용할 수 있다. 엄격한 비수정이 필요하면 별도 읽기 전용 환경이 필요하다: 역할의 edit 거부만으로 shell 등 다른 쓰기 경로가 차단되지는 않는다.
- Build는 상황에 맞게 접근성·반응형·데이터·오류 상태 등 필요한 검사와 도구를 선택한다. 렌더 실패는 미확인으로 남긴다. 증거는 [증거팩](evidence-pack.md)을 활용할 수 있으며 최종 제품 수용은 사람이 판단한다.
- V-suite 6/6은 제한된 시드 결함 탐지 결과이지 실제품 자율 판단 능력이나 전반적 모델 품질의 입증이 아니다.

### 정본과 과업 계획 (2026-11-08)

- 지속되는 사실은 프로젝트 정본(제품·경험·디자인·시스템·상태)에 두고, 과업별 계획은 짧게 시작해 작업 중 갱신한다. 모든 것을 구현 전에 문서화하지 않는다. 책임 구분과 작업 규모별 확정 범위는 [프로젝트 지식](project-knowledge.md#계획정본작업-상태의-분리)을 따른다.
- 계획은 Build가 소유하고 Plan·Explore는 근거를 보탤 수 있다. 승인 단계가 아니며 계획의 존재는 완료 기준이 아니다. 실제 동작·렌더·검증 결과로 판정한다.
- 구현·렌더 중 발견한 사실이 과업을 넘어 유효하면 해당 정본에 반영하고, 이후 작업을 구속하는 결정만 결정 기록으로 승격한다. 같은 사실을 계획과 정본에 복사하지 않는다.

### 화면 구조·표현 선택 (2026-11-08)

형태는 데이터의 성격과 사용자가 하려는 일에서 출발한다. 이 판단은 **정보 우선순위나 화면 구조가 아직 확정되지 않았을 때** 적용한다. 문구·오타·이미 확정된 컴포넌트 재사용은 바로 구현하고, 새 화면·구조 변경·정보 우선순위가 불확실한 변경에서만 아래 순서를 쓴다.

1. 사용자 목표·업무: 누가 어떤 판단을 하고 어떤 행동으로 끝나는가.
2. 정보의 성격과 핵심 행동: 비교·정렬, 긴급 발견, 기한·경과, 기간 추세, 공간 분포, 계층 탐색, 상태 이동, 목록 유지 + 상세 확인 중 무엇인가.
3. 구조·표현 탐색: 그 행동에 맞는 기존 패턴을 고른다. 표·목록·우선순위 큐·타임라인·캘린더·차트·지도·트리·인스펙터·분할 보기·보드·스텝퍼·카드 등이 후보이다.
4. 구현 후 재평가: 실제 렌더에서 그 구조가 과업을 실제로 도왔는지 본다. 구조가 틀렸으면 여백·색을 반복 수정하지 않고 정보구조·레이아웃 변경을 제안한다.

- 판단 순서는 강제 절차가 아니라 사고 순서다. 단순 수정·이미 승인된 구조에서는 생략한다.
- 비교가 필요한 작업에서만 서로 다른 구조를 검토한다. 모든 화면에 3안을 만들지 않는다.
- 일관성은 컨트롤·타이포·간격·모션 같은 디자인 시스템 규칙에서 유지하고, 화면 구조는 업무에 따라 달라져도 된다.
- Build는 구조 판단이 확정되지 않은 UI 변경에서 이 순서를 직접 적용하고, 필요하면 독립 읽기 전용 검토를 한 번 요청한다. 구현·통합·검증은 계속 Build가 소유한다.
- 결정론적 검사(대비·타입 스케일·오버플로·접근성·성능)는 싸고 반복 가능한 근거이므로 먼저 돌린다. 다만 통과가 과업 적합성의 증거는 아니다. 예: 정렬 축이 ID로 고정된 화면은 검출기에서 0건이 나온다.
- 방향·레퍼런스가 필요하면 Oil UI·Impeccable·Mobbin·oh-my-design 같은 외부 자산을 프로젝트별로 고른다.

### 외부 UI 전문 도구 선택 (파일럿)

- 새 화면의 방향·구조 탐색에는 Oil UI를, 기존 제품 개선에는 Impeccable을 프로젝트별 선택지로 검토한다. Mobbin은 실제 제품 참고, 브라우저·Playwright는 실행 검증을 맡는다. Oil UI는 아직 전역 채택하지 않았다.
- Build가 목표·권한과 검증을 소유한다. UI 방향·구조 판단도 Build가 맡고, 필요한 경우에만 독립 읽기 전용 검토를 쓴다. 구현은 Build/General이 맡는다. 외부 스킬의 필수 자식 생성·점수 기준·승인 절차는 KSI의 권한과 사용자 지시보다 우선하지 않는다.
- 좁은 화면 요소 피드백은 Selector를 격리 환경에서 선택적으로 검토하고, 출력의 선택자와 실제 코드 위치를 대조한다. DOM·복사 내용에 민감정보가 포함될 수 있다. Crit는 계획·diff·앱에 대한 사람의 리뷰라는 별도 용도로 비교하되 외부 공유와 명령 실행 경계를 먼저 확인한다.
- draw-ui는 이미지 시안이 필요한 경우에만 고려하며 이미지 생성·전송과 의존성 설치는 별도 확인한다. Chrome DevTools MCP는 기존 브라우저 도구로 부족한 진단에 한정해 통계·외부 조회 설정을 확인한다. Superpowers는 기존 스킬과 겹치지 않는 부분만 비교한다. Promptfoo의 OpenCode V2 호환성과 실과업 평가 효용은 아직 미검증이다.
- 도입 전 동일 초기 코드·목표에서 사용자 과업, 기능·데이터 보존, 실제 렌더, 수정 횟수와 측정된 시간·비용을 비교한다. 가능하면 사람이 도구 이름을 모른 채 평가한다. 설치·자동 점수만으로 품질 개선을 인정하지 않는다. 파일럿 범위와 한계는 [검증 기록](validation.md)을 따른다.

### 담당 선택 기준 (작업 성격별)

- 직접 처리: 맥락이 강하게 결합되어 있거나, 위임보다 직접 완수가 빠른 작업 (핵심 기능·구조 개편, DB·API·UI 동시 변경 포함).
- General 위임: 목표와 변경 경계를 명확히 정의할 수 있고, 독립적으로 구현·검증·인수할 수 있는 작업 (독립 기능 완결·원인 특정된 버그·테스트 작성. 파일 수·규모 무관).
- 조사는 Explore에, UI 구조·표현 판단은 Build에 둔다. 독립 검토가 필요하면 읽기 전용 세션을 한 번 쓴다.
- 같은 모델을 쓰면 위임이 지능·비용을 자동 개선하지 않는다. 전달+통합 비용이 들고, 호출 비율 강제나 전부 넘기기 규칙은 두지 않는다.

### General 작업 지시 형식

구현 방법을 상세 지정하지 않고 목표·맥락·경계·완료 기준을 준다. 예:

> 검색·필터 기능을 완성하라. 기존 목록 조회 API와 상태 관리 구조를 유지하고, 검색어와 상태 필터 조합이 동작하게 구현한다. 범위는 검색·필터 컴포넌트와 테스트이며, 공유 API 계약·다른 화면 구조는 임의 변경 금지. 정상·빈 결과·오류 상태를 검증하고 발견 문제는 수정 후, 변경 내용·테스트 결과·통합 필요사항을 반환하라.

General은 범위 안에서 함수 구성 등 구현 방식을 스스로 결정하고, 동작·상태·테스트를 완성해 반환한다. 같은 파일을 두 에이전트가 동시에 고치지 않으며, 병렬 시 worktree·책임 분리 규칙을 따른다.

### Decisions 판단 보조 (읽기 전용 권고)

Build가 직접 구현·위임·병렬·추가 검토를 판단하기 전에 Jev 권고를 참고할 수 있다. 서버 API를 직접 호출하며 별도 플러그인·모델 고정은 없다:

```sh
opencode api post /api/experimental/generate/decisions --data '{
  "model": {"providerID": "opencode", "id": "jev-1.13-free"},
  "input": [{"type": "text", "text": "<작업 맥락>"}],
  "questions": [
    {"type": "choice", "name": "execution_strategy", "instructions": "어느 배정이 나은가",
     "choices": [{"value": "direct"}, {"value": "delegate_general"}, {"value": "parallel"}]},
    {"type": "predicate", "name": "needs_review", "instructions": "독립 검토가 이 과업을 의미 있게 개선할 것이다"}
  ]}'
```

Jev는 decision 모델이라 `/api/model`(기본 chat 조회)에 나오지 않는다. `/api/experimental/generate/decisions`로 호출하며, 2026-11-08 이 환경에서 predicate 응답과 cost 0을 확인했다.

원칙: Jev는 권고만 하며 최종 선택은 Build가 한다. Build 선판단을 먼저 기록하고 Jev와 비교한 뒤 실행 결과로 평가한다(`decision-log.md` 형식). API 실패 시 Build 정상 진행을 막지 않는다. 자동 모델 변경·권한 승인·도구 가로채기는 하지 않는다.

### 선택형 AI PR 리뷰 (2026-11-08)

- `.github/workflows/opencode-review.yml`은 **선택형 읽기 전용** 리뷰입니다. `OPENCODE_REVIEW_ENABLED=true`일 때만 PR에서 실행되고, 수동 실행은 Actions에서 항상 가능합니다.
- `OPENCODE_API_KEY`(OpenCode Go/Console 키)가 필요합니다. 없거나 변수가 꺼져 있으면 실행되지 않으며 CI를 막지 않습니다.
- 모델은 `OPENCODE_REVIEW_MODEL` 변수로 바꿀 수 있습니다. 기본값은 무료 `opencode/deepseek-v4.1-flash-free`입니다.
- 파일 수정·푸시·승인·병합 권한은 없습니다. 코멘트만 남깁니다.
- 리뷰 결과는 Build가 triage하고, 수정·재검증·병합은 기존 흐름대로 사람이 결정합니다.

### 화면 작업 흐름 (새 화면·리디자인)

1. **현재 화면 실행**: 코드를 읽고 짐작하지 말고 실제 화면을 렌더·실행합니다.
2. **레퍼런스 조사**: 유사 업무의 실제 제품 화면을 Mobbin 등으로 조사합니다.
3. **방향 결정**: 레퍼런스와 현 제품 구조를 비교해 디자인 방향을 정하고, 기존 디자인 시스템과 일관성을 유지합니다.
4. **대표 화면 먼저 (새 제품·대규모 개편)**: 화면 전체를 만들기 전에 대표 화면 하나를 실제로 구현·검증해 방향을 재확인합니다. 작은 변경은 이 단계를 생략합니다.
5. **구현**: Build 또는 General이 기능·데이터 연결을 보존하며 구현합니다. 방향 정리나 독립 검토는 과업에 도움이 될 때 선택합니다.
6. **검증·수정**: 실제 사용자 과업, 첫 화면·주요 동작과 관련 로딩·빈·오류 상태를 확인하고 중요한 결함을 수정·재검증합니다. 필요시 독립 검토와 증거팩을 활용합니다. 검증하지 못한 상태는 분명히 남깁니다.

| 웹 | agent-browser (로컬 Chrome, ref 루프·프로필·추적) | 내장 브라우저 도구(무설치), `playwright-cli` 스킬(복잡한 시나리오) |

둘의 가치는 기능 개수가 아니라 **웹·네이티브를 같은 사용법**(스냅샷 ref → 행동 → 재읽기 → 검증)으로 다루는 데 있습니다. 이 Mac 설치 기록: `npm -g agent-browser@0.41.2`·`agent-desktop@1.2.0`, Chrome for Testing 157.0.8103.38. 공유 소스·전역 MCP 설정은 바꾸지 않았습니다.

사용 규칙:

- 기본은 **headless + 재읽기 검증**입니다. AX 리턴 코드만으로 효과를 판단하지 않습니다(공식 문서 원칙). 클릭 5회가 `succeeded`여도 스냅샷에서 표현식·결과값을 다시 읽어 확인합니다.

- MCP로 연결하면 Plan/Explore deny 패리티(`cua-driver_*`와 동일 규칙)를 적용합니다. CLI 경유 사용은 shell 권한으로 동작하므로 역할 제한을 별도로 확인합니다.
- 로그인 상태·클립보드·개인정보가 포함된 출력은 공개 로그에 올리지 않습니다. [검증 기록](validation.md#agent-browseragent-desktop-파일럿-2026-11-06-로컬-한정)을 따릅니다.

## 이 환경의 알려진 제약

- **DGX General:** LAN `172.30.1.44`는 macOS Local Network Privacy가 `node`를 허용하기 전까지 Node에서 `EHOSTUNREACH`입니다. 현재는 Tailscale `100.116.163.1` 경로를 사용합니다. Tailscale이 끊기면 General 호출이 실패하며 자동 fallback은 없습니다.
- **Go Explore:** Go 한도 실패가 날 수 있습니다. 자동 재시도·다른 제공자 전환은 하지 않습니다.
- **설치기:** 관리 파일 교체에는 범용 Node/POSIX CAS가 없어, 마지막 검사 뒤 비협조 writer와의 경합이 남습니다. 잠금이 남으면 자동 삭제하지 말고 [설치 잠금 복구](installation.md#설치-잠금과-중단-복구)를 따릅니다.
- **Native 연결:** 이전 F1~F3 실험은 모델 픽스처의 스트림에 종료 사유가 빠져 Native가 출력을 거부·재시도했으므로 업스트림 결함의 확정 증거가 아니다. 정상 스트림의 격리 재실행에서는 진행 중 `wait` 요청 중단 후 같은 세션의 응답, fork 후 응답, queue 전달을 확인했다. 이전 fork 검사는 응답 문자열도 잘못 비교했다. 이는 해당 조건의 실측이지 모든 버전·경합에서 결함이 없다는 뜻은 아니다. Events는 휘발성 알림이므로 끊김 후 재구독하고 실제 세션 상태와 메시지를 다시 조회한다. 메시지만으로 idle을 추론하지 말고 실행 상태·권한 대기·최근 메시지를 함께 확인하고 불확실하면 전송을 보류한다.
- **복구 안전:** 응답 타임아웃은 손상 확정이 아니다. 모델 지연·권한 대기·연결 문제·실패·실행 여부를 구분하고, 기존 작업 종료를 확인하며 미반영 변경을 보존하기 전에는 대체 작업을 시작하지 않는다. 복구 불가가 확인되면 승인된 범위에서 새 세션에 목표·제약·상태·기존 변경과 Git 기준을 전달한다. `instructions.entry`는 보조 기록이며 작업 결과나 복구 성공의 증거가 아니다.
- **시각 캡처:** 이미 시작된 OS I/O는 즉시 취소되지 않고, 성공한 임시 캡처의 자동 디스크 GC는 없습니다.
- **평가기:** 문장 기반 heuristic이며, 실제 검사 종료 코드·도구 상태를 별도로 확인합니다.

## 장기 작업 개선 순서

선택형 `ksi_session_observe`는 직접 소유한 자식만 대상으로 Native 이벤트와 세션·권한 스냅샷을 대조한다. `waitMs`를 주면 최대 30초 동안 관련 이벤트를 기다린 뒤 다시 조회한다. 타임스탬프는 서버 재시작 뒤 오래될 수 있고 `running_or_stalled`는 실행 중인지 고장인지 구분하지 못한다. 조회와 후속 조치는 원자적이지 않으며 도구는 프롬프트·중단·재위임을 실행하지 않는다. Build가 해당 worktree와 변경을 확인하고 Native 도구로 다음 행동을 결정한다. 설치는 [설치 안내](installation.md)를 따른다.

1. 격리 Native 서버와 scripted 모델에서 이벤트 수신·단절 후 상태 재조회, compaction 이후 새 응답을 확인한다. 성공과 알려진 결함 재현을 구분하며, 실모델·제품 품질의 증거로 쓰지 않는다.
2. 실측된 Native 표면만으로 최소 관찰·복구 연결을 설계한다. 이벤트는 힌트이고 현재 상태가 확인 기준이다. 중복 실행 방지, 권한 대기·오류 구분, 기존 변경 보존을 우선한다. 자동 재시도·모델 전환·새 필수 엔진은 도입하지 않는다.
3. 실제 제품 과업 하나에서 구현·필요한 독립 검토·통합·실패 후 이어가기와 사용자 과업을 평가한다. 역할이나 도구 호출 횟수는 성공 기준이 아니다.
4. 격리 PR 파일럿에서 독립 리뷰 → Build의 수용·기각 판단 → 수정·재검증 → 사람 수용을 확인한다. 실제 저장소 설정, 자격 증명, 유료 호출 및 배포는 별도 권한이 필요하다.

## 테스트 추가

- 오프라인 회귀는 `tests/*.test.mjs`로 추가하면 `--offline`이 자동 발견합니다. `-live.mjs`·`-native.mjs`는 자동 포함하지 않습니다.
- 새 Native 스크립트는 `scripts/verify-harness.mjs`의 `nativeScripts` 목록에 명시해야 `--native`에 포함됩니다.
- 테스트는 실제 제품 코드·공유 세션·자격증명을 건드리지 않고, 자체 임시 fixture를 사용합니다.
