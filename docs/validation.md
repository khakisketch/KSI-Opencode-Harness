## 동적 8개 역할과 최대 깊이 3 (2026-10-24)

사용자가 Native **Plan·Build·General·Explore** 유지, Custom **Research·Design·Engineer·Critic** 구성, Plan/Design `all`, 최대 깊이 3의 동적 위임을 확정하고 개선·전역 적용·배포를 요청했습니다. 이는 이름만 바꾸는 작업이 아닙니다. `design-architect`의 UI 단위 완결 책임은 `design`으로, `ux-scout`의 관찰·패턴 분석은 범용 `research`로 이전하고, `ui-ux-critic`과 `product-reviewer`의 독립 검토를 `critic`에 통합합니다. 시스템 기술 단위는 `engineer`가 맡고, 초기 `architect` 파일은 원본 그대로 `docs/archive/agents/architect.md`에 보존해 발견·호출 대상에서 제외합니다. 아래 날짜별 이전 명칭·모델·검사 수는 당시 기록으로 보존합니다.

현행 배정은 운영 역할 전체가 `opencode-go/muse-spark-1.3-contributor`를 사용하고 Plan·Critic=XHigh, Engineer·Design·General=High, Research=Medium(시험 배정), Explore=Low입니다. Build는 세션 선택을 따릅니다. 모델 카탈로그에서 활성 ID와 Variant 지원을 확인했으며 성능 비교 결과로 확대하거나 기존 세션 모델을 강제로 바꾸지 않습니다. 이전 Sol·DeepSeek·GLM·MiMo·Luna 배치는 당시 실행 기록으로만 남습니다.

루트는 깊이 0, 상한은 3이며 일반 작업은 1~2단계를 사용하고 유용한 필요가 있을 때만 3을 사용합니다. 고정 파이프라인·별도 라우터·강제 전원 호출은 없습니다. Build·Plan·Engineer·Design은 허용 전문가를 선택하고, Plan은 Explore·Research·Critic만 호출합니다. Research는 Explore에 한정된 추출을 맡길 수 있습니다. General·Explore·Critic은 말단입니다. 자기 호출·미등록 대상 거부와 깊이 상한을 유지합니다. 각 부모가 자식 결과를 해석·검토·통합하며 원요구·확정 계약·분석/구현 범위·원본 경로·버전·환경을 하위까지 전달합니다. 공유 파일·상태·브라우저는 한 변경 소유자를 두고 중복 조사를 피하며 기존 담당 세션으로 교정합니다.

Build는 제품 실행·다음 개발·통합·최종 인수를, Plan은 요구·우선순위·계획과 계획 조사를, Engineer는 기술 단위의 설계·구현·테스트·복구·반복 개선을, Design은 UI 단위의 진단·설계·구현 조율·렌더 교정을 책임집니다. Engineer와 Design은 필요할 때 직접 협업하되 같은 과업을 조상에게 되돌리지 않습니다. Critic은 배정된 제품·UX·코드·아키텍처 질문에 맞는 근거·설치 스킬로 비평하고, 제품 과업의 저장·복귀·실패 복구·누락·성급한 완료 주장 검토를 보존합니다. 최종 인수나 구현을 맡지 않으며 중요한 독립 검토는 해당 설계/구현에 참여하지 않은 새 세션에 맡깁니다.

**Plan의 Native 프롬프트·역할별 편집 거부는 보존하지만, 이 역할 규칙이 하위에 자동 상속되지는 않습니다.** 별개의 Native 세션별 제한은 생성 시 자식에게 상속할 수 있습니다. 계획·분석만 승인됐으면 하위도 그 범위를 지키고, 엄격한 보호가 필요하면 기존 거부를 보존한 제한 세션 또는 제한 환경을 하위 생성 전에 준비해 실제 효과를 확인합니다. Plan 선택만으로 이를 자동 적용하거나 기존 자식에 소급 적용하는 기능을 추가하지 않았습니다. 지침·역할 이름·모의 검사로 모든 OS/네트워크 경로의 샌드박스를 보장하지 않습니다.

Research·Critic은 기본 거부 후 필요한 읽기·웹·Browser·Code Mode·Context7의 문서 조회 2종·역할별 설치 스킬과 고유 CLI 탐색/입력/캡처만 허용합니다. Research의 Mobbin 검색 3개 및 그 외 Mobbin 승인 요구는 유지합니다. 제품/보고서 편집·임의 Shell·설치·서버·배포·자격증명·프로필/인증 상태 가져오기·다른 세션/전역 종료는 거부합니다. Browser·execute·CLI는 읽기 전용 샌드박스가 아니며 승인된 환경·계정·상태 전이만 사용합니다. 새 외부 스킬이나 도구를 일괄 설치하거나 기존 원문을 고치지 않습니다.

검증은 (1) 모의 회귀, (2) 실제 설치본·Native 모델/모드/권한, (3) private HOME/XDG와 로컬 scripted model을 사용하는 Native 중첩 실행으로 구분합니다. `tests/delegation-native-integration.mjs`는 새 역할의 실제 정본을 복사하고 모델만 로컬 fixture로 대체해 Plan의 재위임, 서로 다른 경로, 깊이 3의 반환과 상한 동작을 확인합니다. 원요구 전달 표식 확인은 전달 검증이지 모델의 이해·판단력 검증이 아닙니다. 실제 제품의 자발적 문제 발견·디자인 품질·장기 완주·비용 절감은 별도 미검증입니다. 최신 확인 환경은 OpenCode **2.1.4 / Linux arm64**입니다.

## 역할 단위·루프·부품 감사 (2026-10-24)

이 감사는 현재 정본과 실제 전역 설치본을 읽고, 역할별 작업 기준·호출 루프·스킬 책임·OpenSpec 사용·프롬프트 중복을 점검한 결과입니다. 모델 품질 비교나 실제 제품 개발 성과를 입증하지 않습니다.

- **Engineer vs General:** Engineer는 미해결 구현 결정·여러 파일/계약/상태·테스트/수리 반복이 있는 다단계 기술 단위를 소유합니다. General은 대상 파일·수정·검증이 이미 정해진 단일 슬라이스만 실행합니다. 발견·설계·조율이 필요해지면 Engineer/Design 소유 단위로 돌아갑니다. 같은 작업을 두 역할이 동시에 소유하지 않습니다.
- **모델 교체와 소유권:** General/Engineer의 구분은 모델 성능·실행 위치가 아니라 작업 단위 소유권으로 유지합니다. General을 Qwen 27B·Qwen Flash Next 같은 로컬 코딩 모델로 바꾸더라도 결정된 슬라이스 실행자라는 계약은 변하지 않으며, 불명확한 기술 단위의 소유권은 Engineer에 남습니다.
- **Design 우선:** 모든 UX/인터페이스 단위는 크기와 무관하게 Design이 소유합니다. 작은 UI 수정도 General이 Design 소유 아래에서 실행할 수는 있지만 디자인 책임은 Design에 남습니다.
- **UI/UX 검토 흐름:** Design이 조사·설계 후 General에 구현을 맡기고, 실제 렌더에서 연구·레퍼런스·설계 의도 반영과 원래 과업을 확인합니다. 중요한 단위는 구현 전 가설 또는 구현 후 결과를 Critic이 독립 비평할 수 있으며, 발견은 Design의 판단을 거쳐 같은 General 세션의 교정·재검증으로 이어집니다. Critic은 필수 게이트가 아니고 수정·인수하지 않습니다. 이는 새 역할·필수 단계를 추가한 것이 아니라 기존 허용 루프를 README에 명시한 것입니다.
- **Explore vs Research:** 경계는 도구가 아니라 질문입니다. Explore는 범위가 정해진 검색·원본 추출, Research는 충돌 자료의 비교·대안·적용 조건·미확인 종합입니다.
- **루프:** Engineer↔Design 직접 호출은 별도 하위 산출물이 있을 때만 유지합니다. 깊이 3, 자기 호출 금지, 조상 왕복 금지가 무한 확장을 막습니다. Plan은 Explore·Research·Critic만 호출하고 Engineer·Design·General에는 직접 위임하지 않으므로, Plan의 분석 전용 범위가 구현 가능 자식으로 새지 않습니다. 엄격한 격리는 자식 생성 전에 명시 세션 제한으로 준비해야 합니다.
- **위임은 인수가 아니다:** 하위 에이전트의 보고는 검증할 증거이지 결론이 아닙니다. 소유자는 실제 결과를 직접 확인하고, 방향·제품 위험이 크면 비용이 들더라도 재조사합니다. Design은 위임 후에도 실제 렌더·상태·상호작용을 검토합니다.
- **지침 중복 정리:** 공통 AGENTS와 역할 파일에 반복되던 증상/문제 정의, 직접 협업, 명령형 스킬 사용, 스킬 필수 단계 문장을 제거하거나 한 곳으로 통합했습니다. Engineer 650→625, Design 1,892→1,845, Critic 1,474→1,457, AGENTS 2,292→2,274 words로 줄였으며, 역할별 권한·검증 계약은 유지했습니다.
- **UX 우선순위:** 화면 문제에서 “어느 것이 가장 거슬리는가” 또는 “어떤 사용자를 우선할 것인가”를 사용자에게 먼저 묻지 않습니다. 제품 맥락·실제 사용 증거로 안전·과업 영향·빈도·복구 난이도를 평가해 우선순위를 정하고, 가정과 기본 계획을 밝힌 뒤 상위 수정을 진행합니다. 제품 범위·계약이 걸린 경우에만 확인합니다. 증상 목록에서 바로 수정으로 가지 않고, 현재 업무 흐름·상태·기기·데이터·기존 패턴을 조사해 관찰 사실과 원인 가설을 분리한 뒤 문제 정의와 성공 조건을 먼저 세웁니다. 비사소한 문제는 문제 정의 전 코드 수정을 금지하고, 사용자의 증상 제보를 명세가 아닌 단서로 검증·반증합니다.
- **Plan 위임:** Plan의 subagent 허용을 Explore·Research·Critic으로 제한했습니다. Engineer·Design·General은 Plan의 직접 위임 대상이 아니며, 구현 가능성이 걸린 질문은 Build로 반환합니다. Plan은 하네스를 분석에 활용하되 구현 가능 자식을 만들지 않습니다.
- **모델:** Engineer·Design=high, Critic=Plan=xhigh, General=high, Explore=low를 유지하고 Research만 medium으로 시험합니다. xhigh 상시 기본의 품질·비용 우위는 미검증이며, Research medium이 비교 품질을 떨어뜨리면 high로 되돌립니다.
- **자체 부품 폐기:** 저장소 번들 `task-first-ux-review` 스킬과 `ksi-impeccable-detector` 편집 훅 플러그인을 제거했습니다. Design은 공식 Impeccable `detect --json` 수동 검사를 사용하고, 네이티브는 소스 검사를 건너뜁니다. 이전 검증 기록의 task-first·플러그인 수치는 당시 이력으로만 보존합니다.

## 브라우저 검증 경로

- 연결된 데스크톱에서는 Native Browser를 우선합니다. 분리된 자식 세션, SSH·헤드리스 환경, 반복 자동화에는 기존 Playwright CLI를 사용합니다.
- 권한과 연결은 별개입니다. 현재 환경의 읽기 전용 조회에서 메인의 `browser.tabs.list`는 성공했지만 General·Architect 자식은 도구가 노출돼도 `browser.disconnected`를 반환했습니다. 두 커스텀 역할의 선언은 `browser: allow`이며 전역 파일에 일괄 차단은 없습니다. 이 관찰은 해당 실행 경로의 자식 미연결 근거이지, 모든 하위 역할이 Native Browser를 원천적으로 못 쓴다는 뜻은 아닙니다. allow 추가만으로 연결이 생기지는 않으며, Native 측 연결 전달 방식은 별도 미확인입니다.
- 도구가 없다고 판단하기 전에 Code Mode 카탈로그에서 필요한 기능을 검색합니다. Native는 `browser.snapshot`으로 요소 ref를 얻고, `browser.tabs.focus`로 탭을 선택한 뒤 보이는 창에서 캡처합니다. DOM/접근성 탐색과 캡처 가능 여부는 별개이며, 이 가시성 조건은 헤드리스 CLI의 요구사항이 아닙니다.
- 캡처가 실패하면 원인에 맞는 허용된 대안을 시도하고 남은 제약을 보고합니다. 담당자가 직접 검수하며, 일반적인 방법 선택·화면 탐색을 사용자에게 넘기거나 코드 분석만으로 시각 검증을 완료했다고 하지 않습니다. 필요한 인증·권한·제품 결정은 사용자에게 요청합니다.
- CLI는 고유한 작업별 세션 이름으로 실행하고 자신이 만든 세션만 종료합니다. 전체 정리용 `close-all`·`kill-all`은 사용하지 않습니다.
- 프로젝트의 Playwright Test, 감사 스크립트, 기존 캡처·로그를 보존하고 산출물 위치·보고 규칙을 따릅니다. 프로젝트 초기화나 테스트 의존성 교체를 하지 않습니다.
- Playwright MCP와 `agent-browser`는 기본 구성에서 제거했습니다. 기존 CLI·Chrome·원본 `playwright-cli` 스킬을 재사용하고, CLI가 없을 때만 공식 `@playwright/cli@0.1.22` 설치를 검토합니다.

Design이 UI 작업의 메인인 경우에도 해당 UI 단위 완결 책임이며 제품 전체 인수로 확대하지 않습니다. Critic이 제품/기술까지 검토해도 최종 인수권을 갖지는 않습니다. Research의 검색 과정은 자신의 세션에 두고 원본·상태·미관측 범위를 포함한 간결한 근거를 넘깁니다.

중요한 UI를 검증 완료로 인수하려면 대상 빌드/상태의 실제 렌더와 관련 조작 증거가 있어야 합니다. `preview` 호출·저장 경로·빌드 통과만으로 대체하지 않으며, 넘침·잘림·콘솔 오류·핵심 흐름은 실제 검사 범위를 확인합니다. 기본 기술 검사 통과는 디자인 합격이 아니고, 증거가 없으면 미검증입니다. 시각적 완성도가 목표라면 그것도 인수 조건이며, 기능 오류가 없다는 이유만으로 종료하지 않습니다. 이는 역할·인수 운영 기준이며 별도 자동 완료 게이트나 CI 강제 기능을 추가한 것은 아닙니다.

기술 수정과 디자인 개선의 반복을 구분합니다. 설계 의도를 바꾸지 않는 기술 결함은 구현자가 자체 실행·수정·재검증하고 Design은 실제 결과에서 효과·회귀·남은 문제를 판단해 다음 개선을 이끕니다. 최신 결과가 불충분하면 직접 재관찰하고 오래된 캡처를 현재 구현의 증거로 삼지 않습니다. 공유 브라우저 소유권과 승인된 테스트 데이터·상태 전이를 지킵니다. 목표 관련 문제가 남고 다음 변경의 개선 근거가 있으면 계속하며 목표·관련 검증을 충족하면 종료합니다. 유효 증거는 재사용하고 횟수 채우기·무관한 취향 변경으로 반복하지 않습니다. 정체 시 원인을 재진단하고 방법·가설·작업 배분을 조정하며 접근·증거·필수 결정·예산 부족은 미완료·차단·미검증으로 보고합니다.
