# 검증 및 적용 범위

기존 브라우저·소스 검사 검증 기록은 2026-10-15 기준 OpenCode **2.0.29 / Linux arm64**에서 확인한 내용입니다. 능력 연결 진단은 2026-10-16에 추가했습니다. 다른 운영체제는 확인하지 않았습니다.

## 능력 연결 진단

필요한 역할·스킬이 없거나 도구 연결이 의심될 때만 실행합니다. 개발의 필수 단계가 아닙니다.

```sh
node scripts/capabilities.mjs
node scripts/capabilities.mjs /path/to/project
```

기존 인증을 사용하는 `opencode api get`으로 Native의 에이전트·개발 스킬 등록과 Context7·Mobbin 연결 상태를 조회하고, 로컬 CLI의 PATH 존재 여부를 확인합니다. 설치·설정 변경·인증·모델 호출·자동 재시도는 하지 않습니다. OpenCode CLI 자체가 필요시 관리 서비스를 시작할 수는 있습니다. 큰 CLI 응답의 파이프 잘림을 피하기 위해 전용 임시 파일로 받아 읽고 정리하며, 응답 원문·오류 원문·설정·토큰은 출력하지 않습니다.

등록은 에이전트별 권한·스킬 자동 노출·실제 실행 성공을 보장하지 않습니다. PATH 존재는 CLI 동작 검증이 아닙니다. 선택 도구의 부재는 실패로 간주하지 않으며, API 조회 실패는 미확인으로 구분합니다. 브라우저 연결·제품 데이터 접근·렌더·모델 품질은 이 명령으로 검사하지 않습니다. 현행 추적 대상은 build·general·explore·plan·design-architect·ux-scout 6개 역할입니다.

진단기의 응답 처리·출력 제한 회귀 검사는 `node --test tests/capabilities.test.mjs`로 실행합니다. 이 검사는 모의 응답을 사용하며 실제 연결을 입증하지 않습니다.

2026-10-16 로컬 실행에서는 추적 대상 역할 5개·스킬 8개 등록, Context7·Mobbin 연결, Node·Playwright CLI·GitHub CLI의 PATH 존재를 확인했습니다. 진단기 검사 20개와 기존 검사 61개가 통과했습니다. 실제 제품 작업이나 장시간 완주를 평가한 결과는 아닙니다.

지식 부족은 공식 자료·사례·스킬, 관찰 부족은 실제 화면·로그·데이터 접근, 실행 부족은 환경·도구·권한, 판단 부족은 전문 역할·독립 검토를 우선 검토합니다. 모델 변경은 실제 과제의 근거와 비용을 확인한 뒤 결정합니다. 이번 진단은 제품 완주 효과 평가가 아닙니다.

## 브라우저 검증 경로

- 연결된 데스크톱에서는 Native Browser를 우선합니다. 분리된 자식 세션, SSH·헤드리스 환경, 반복 자동화에는 기존 Playwright CLI를 사용합니다.
- 권한과 연결은 별개입니다. 현재 환경의 읽기 전용 조회에서 메인의 `browser.tabs.list`는 성공했지만 General·Architect 자식은 도구가 노출돼도 `browser.disconnected`를 반환했습니다. 두 커스텀 역할의 선언은 `browser: allow`이며 전역 파일에 일괄 차단은 없습니다. 이 관찰은 해당 실행 경로의 자식 미연결 근거이지, 모든 하위 역할이 Native Browser를 원천적으로 못 쓴다는 뜻은 아닙니다. allow 추가만으로 연결이 생기지는 않으며, Native 측 연결 전달 방식은 별도 미확인입니다.
- 도구가 없다고 판단하기 전에 Code Mode 카탈로그에서 필요한 기능을 검색합니다. Native는 `browser.snapshot`으로 요소 ref를 얻고, `browser.tabs.focus`로 탭을 선택한 뒤 보이는 창에서 캡처합니다. DOM/접근성 탐색과 캡처 가능 여부는 별개이며, 이 가시성 조건은 헤드리스 CLI의 요구사항이 아닙니다.
- 캡처가 실패하면 원인에 맞는 허용된 대안을 시도하고 남은 제약을 보고합니다. 담당자가 직접 검수하며, 일반적인 방법 선택·화면 탐색을 사용자에게 넘기거나 코드 분석만으로 시각 검증을 완료했다고 하지 않습니다. 필요한 인증·권한·제품 결정은 사용자에게 요청합니다.
- CLI는 고유한 작업별 세션 이름으로 실행하고 자신이 만든 세션만 종료합니다. 전체 정리용 `close-all`·`kill-all`은 사용하지 않습니다.
- 프로젝트의 Playwright Test, 감사 스크립트, 기존 캡처·로그를 보존하고 산출물 위치·보고 규칙을 따릅니다. 프로젝트 초기화나 테스트 의존성 교체를 하지 않습니다.
- Playwright MCP와 `agent-browser`는 기본 구성에서 제거했습니다. 기존 CLI·Chrome·원본 `playwright-cli` 스킬을 재사용하고, CLI가 없을 때만 공식 `@playwright/cli@0.1.22` 설치를 검토합니다.

해당 환경에서는 Native Browser로 외부 페이지 열기·캡처·기본 클릭을 확인했습니다. 전역 Playwright MCP를 비활성화한 뒤 Design Specialist 자식 세션에서 CLI 0.1.22를 `DISPLAY`·`WAYLAND_DISPLAY` 없이 실행해 외부 화면, 로컬 상태 전환, PNG 3개 읽기를 확인했습니다. 자식 세션이 끝난 뒤 별도 보호 세션도 유지됐습니다. 이는 브라우저 경로 확인이지 실제 제품 UI의 품질 검증은 아니며, 다른 OS나 전체 원격 SSH 환경의 검증을 의미하지 않습니다.

### Scout CLI 호출·권한 보정 (2026-10-21)

10/20 실프로젝트의 Scout는 `playwright-cli -s=ux-scout-… open <url>`에서 `Permission denied: shell`을 받았고, 실시간 탐색을 하지 못했다고 보고했습니다. 기존 허용 목록은 인수 없는 `open`만 허용했으나 설치된 CLI 0.1.22는 두 호출 형식을 모두 지원합니다. `open <url>`도 허용하도록 맞추고, 같은 명명 세션의 `fill/type/select/check/uncheck/go-back/go-forward/reload`를 허용했습니다.

제품 편집·임의 Shell·추가 위임은 계속 거부하며 `run-code/eval`, 사용자 config/profile, 영구 프로필, 다른 세션 attach, 인증 상태 가져오기, 업로드, 전역 종료는 허용하지 않습니다. 추가 `-s=`로 세션을 바꾸는 명령도 거부합니다. 기존 CLI와 브라우저를 재사용하며 `agent-browser`나 새 MCP는 추가하지 않았습니다. 명령별 Native 권한 평가는 76개 통과했으며, 이는 네트워크/파일시스템 샌드박스나 실제 브라우저 실행의 증거를 대신하지 않습니다.

실제 하위 Scout(`openai/gpt-6-luna-fast#high`, OpenCode 2.1.1 / CLI 0.1.22 / Linux arm64)로 격리된 loopback 화면을 확인했습니다. Native `tabs.list`는 도구가 노출돼도 여전히 `browser.disconnected`였으며, 이 연결 전달 문제를 해결했다고 주장하지 않습니다. 자신의 CLI 임시 세션에서는 `open <url>`·`goto`·입력(`fill/type/press`)·선택·체크/해제·클릭·뒤로/앞으로·새로고침과 390×844 PNG 저장·원본 판독을 완료했습니다. 메인도 같은 PNG를 읽고 서버의 입력/선택 이벤트·두 번의 history 이동·reload 후 값 유지를 대조했습니다. 별도 보호 브라우저 세션은 종료되거나 값이 바뀌지 않았고 픽스처 소스 해시도 불변이었습니다.

첫 입력은 잘못 옮긴 ref(`e1e7`)로 한 번 실패했고 snapshot의 실제 ref(`f1e7`)로 교정해 성공했습니다. 권한 거부를 우회하거나 임의 스크립트를 실행한 것은 아닙니다. 최초 `open` 출력의 콘솔 오류 1건과 최종 `console`의 0건은 구분해 기록했으며, 세션 전체에 오류가 없었다고 일반화하지 않습니다. 자신의 CLI 세션만 닫았고 보호 세션과 fixture 서버는 메인이 따로 정리했습니다. 원본 기록·서버 이벤트·PNG·검증 요약은 `/tmp/opencode/ksi-scout-browser-pFTXlz/`에 있습니다.

이는 이번 명령·환경의 접근 경로 smoke이며 실제 제품 UX, 인증된 고객 환경, 다른 OS·하위 세션 전체의 Native 연결을 보장하지 않습니다. 스킬 호출·성능 검사는 하지 않았고, 제품 파일·실데이터·다른 프로젝트의 브라우저 상태는 변경하지 않았습니다.

## 디자인 판단의 적용 범위

제품 개발은 기본 Build가 제품 목표·통합·최종 인수를 소유합니다. 중요한 UI는 Design Architect가 직접 관찰·개선 우선순위·설계·렌더 재평가를 주도하고 General이 코딩·실행·기술적 결함 수정을 맡는 것을 기본으로 합니다. UX Scout는 선택형 하위 조사이며 넓은 관찰·문제 후보·Mobbin/외부 참고와 원본 근거를 간결히 넘기고, 설계 승인·제품 코드 작성·완료 인수는 하지 않습니다. 전역 `experimental.subagent_depth=2`(기본값 1)는 Build→Architect→작업자(General·Scout·Explore)의 한 단계 중첩을 허용하는 최대치이며, 매번 깊은 트리를 강제하지 않습니다. Architect는 맡은 UI 단위를 통째로 소유해 작업자 세션을 직접 호출·재사용하며 구현·렌더·검토를 잇고, 매 반복마다 Build를 거치지 않습니다. Architect는 이정표·결정·충돌·실제 차단 사유와 최종 통합 증거를 반환하고 전체 대화 이력을 복사하지 않습니다. Build는 목표·범위 변경이나 역할 간 충돌·최종 인수에 개입하며 일상적인 설계 승인은 요구하지 않습니다. 작은 수정·밀접한 작업이나 명시적으로 맡긴 구현은 직접 처리할 수 있습니다. UI 중심 작업은 선택된 Design Architect가 메인으로 책임질 수 있습니다(`mode: all` 유지). UX Scout는 선택형이며 메인 또는 맡은 단위 안에서는 Architect가 직접 호출합니다. Plan은 선택형 기술 자문이고 매번 호출하지 않으며, Explore 조사만 위임하고 General·Architect를 두 번째 구현 책임자로 호출하지 않습니다. Build는 장기 연속성을 세션·이력·프로젝트 자료로 유지하고, 큰 전환·상당한 곁작업 후 복귀·국소 정체·장기 목표 완료 판단 전에 Plan에 방향·누락·남은 작업 점검을 요청할 수 있습니다. Plan은 승인 관문이나 기억 저장소가 아닙니다. [공식 Subagent 도구](https://opencode.ai/v2/docs/tools#subagent)

설계 인계는 관찰한 문제·사용자 영향과 화면 구성·정보 우선순위·레이아웃 관계·상태/상호작용·보존할 의도·구현 재량이 실제 구현에 충분한 수준이어야 합니다. 고정 양식이나 모든 픽셀의 선결정은 요구하지 않습니다. 구현자는 실제 코드·화면의 제약과 충돌하는 가설을 근거로 조정할 수 있지만 핵심 의도와의 충돌·변경 이유를 반환해야 합니다. 디자인 담당자는 코드를 누가 썼든 요구·의도와 실제 렌더를 대조해 품질을 책임지고, 메인은 설계 충실도와 별개로 원래 문제 해결 여부를 판단합니다. Architect도 필요하면 브라우저·Mobbin을 직접 확인합니다. 같은 설계자의 검토는 완전히 독립적인 설계 평가가 아닙니다. Scout의 시끄러운 조사 과정은 자신의 세션에 두고, 원본 이미지·URL·상태와 미관측 범위를 포함한 간결한 후보만 넘깁니다.

중요한 UI를 검증 완료로 인수하려면 대상 빌드/상태의 실제 렌더와 관련 조작 증거가 있어야 합니다. `preview` 호출·저장 경로·빌드 통과만으로 대체하지 않으며, 넘침·잘림·콘솔 오류·핵심 흐름은 실제 검사 범위를 확인합니다. 기본 기술 검사 통과는 디자인 합격이 아니고, 증거가 없으면 미검증입니다. 시각적 완성도가 목표라면 그것도 인수 조건이며, 기능 오류가 없다는 이유만으로 종료하지 않습니다. 이는 역할·인수 운영 기준이며 별도 자동 완료 게이트나 CI 강제 기능을 추가한 것은 아닙니다.

기술 수정과 디자인 개선의 반복을 구분합니다. 설계 의도를 바꾸지 않는 기술 결함은 구현자가 자체 실행·수정·재검증하고, Architect는 실제 결과에서 효과·회귀·남은 문제를 판단해 다음 개선의 우선순위·설계를 제시합니다. 최신 결과가 불충분하면 직접 재관찰하며, 오래된 캡처를 현재 구현의 증거로 삼지 않습니다. 공유 브라우저는 소유권을 조율하고 데이터 변경이 필요한 관찰은 테스트 환경·데이터를 사용합니다. 목표 관련 문제가 남고 다음 변경의 개선 근거가 있으면 계속하고, 목표·관련 검증을 충족하면 종료합니다. 유효 증거는 재사용하며 횟수 채우기나 무관한 취향 변경으로 반복하지 않습니다. 정체 시 원인을 재진단하고 방법·가설·작업 배분을 조정하며 필요할 때만 독립 검토를 사용합니다. 접근·증거·필수 결정·실행 예산이 부족해 멈춘 상태는 미완료·차단·미검증으로 보고합니다.

중요한 UI 작업은 구조·핵심 조작을 정하기 전에 사용자 과업·사용 조건·실제 화면·관련 제품 사례를 근거로 판단합니다. 스스로 불확실하다고 느끼는지보다 충분한 근거가 있는지를 기준으로, 기존 유효 근거를 재사용하거나 부족한 근거를 조사합니다. 기계적 수정에 불필요한 조사를 붙이거나 매번 새 외부 조사·와이어프레임·승인을 요구하지 않습니다.

개선 범위는 사용자가 열거한 수정 목록이 아니라 승인된 목표로 판단합니다. 관련 화면·공유 컴포넌트·연결 흐름의 필요한 개선은 담당자가 수행하고 검증합니다. 명시적 제외를 지키고, 목표 확대나 계약·비용·보안·데이터 정책 변경이 필요한 경우에만 결정을 확인합니다. 무관한 문제는 보고하되 임의로 새 과제로 삼지 않습니다.

`default_agent: build`는 에이전트를 지정하지 않은 세션의 기본값입니다. 기존 세션의 선택을 바꾸지 않으며 프로젝트별 설정은 이를 재정의할 수 있습니다. ## 긴 세션 Compact 연속성 검사 (2026-10-17)

플러그인이나 별도 도구 없이, 공식 수동 Compact API(`POST /api/session/{id}/compact`)로 장기 작업 연속성이 유지되는지 확인했습니다. 검사 파일은 `tests/compaction-continuity-live.mjs`(선택형 실모델, 현재 연결된 `deepseek-v4.1-flash#max` 사용, 계정 사용량 소비)와 `tests/compaction-continuity.test.mjs`(순수 단위 검사 32개, 모델 호출 없음)입니다.

방법: 변형별 새 세션 1개에 같은 대본을 실행했습니다. 목표·확정 결정·미확정 후보·마일스톤 상태 제시 → 첫 작업(m2.py 생성) → 약 11k 토큰 로그로 목표 턴을 보존 tail 밖으로 밀기 → 수동 Compact #1 → 기억만으로 상태 점검(목표/확정/미확정 혼동 여부/완료·미완료/다음 단계) → 추가 작업(m3.py) → 무관한 곁작업 → 수동 Compact #2 → 원래 개발 복귀 지시. 변수는 픽스처 프로젝트 설정의 `compaction.keep.tokens` 하나입니다(현재값 8192 vs Native 기본 15000, `buffer`는 양쪽 동일). 판정은 결정적 채점(토큰 복원 여부, 미확정 혼동, 재읽기·재작업 여부)이며 근거는 변형별 `evidence.json`과 원본 메시지 덤프로 `/tmp/opencode/ksi-compaction-2026-10-17/`에 있습니다.

결과: 두 변형 모두 통과했습니다.

- Compact 1·2 모두 `completed`. 요약(1.4~2.1KB)에 목표·파일명 결정(`orders-YYYYMMDD.csv`)·진행 방식 결정(전역 리팩터 대신 국소 모듈)·미확정 후보(배송비)가 포함됐고, 원래 목표 턴은 두 변형 모두 보존 tail에 남지 않았습니다(요약 의존 보존).
- 상태 점검은 두 변형 모두 파일 재읽기 없이 6개 항목을 정확히 복원했고, 미확정 후보를 확정처럼 다루지 않았습니다.
- 복귀 지시 후 두 변형 모두 `python3 check.py`를 실제 실행하고 원래 작업(CSV 내보내기 모듈 구현)을 이어갔으며, 완료된 모듈을 다시 만들지 않았습니다(재작업 0건).
- 비용은 변형당 약 $0.04, 소요 약 5~6분입니다.

판단: 이 시나리오에서 현재 설정(8192/4096)의 문제가 확인되지 않아 설정을 유지합니다. 명시적 Compact 요청 도구(플러그인)는 필요성 근거가 없어 도입하지 않았고, 선택적 정리 플러그인(DCP 등)은 별도 실험군으로 보류합니다. 문제가 드러나면 원인을 압축 시점·요약 내용·위임 중 어디에서 왔는지 구분한 뒤 필요한 부분만 수정합니다.

한계: 변형당 단일 사례이므로 일반화할 수 없습니다. 자동(한도 도달) Compact 경로, 실제 장기 프로젝트의 반복 압축, 다른 모델·컨텍스트 크기, 캐시 비용 변화는 검사하지 않았습니다. 픽스처는 shell 권한을 좁게 제한했으므로 모델이 허용된 명령으로 우회하는 과정이 포함됐지만(두 변형 모두), 이는 압축과 무관한 픽스처 조건입니다.
