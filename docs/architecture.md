# Native OpenCode V2 architecture

KSI now has two parts: four custom role templates and a standalone installer. The installer renders ordinary V2 `agents/*.md` files into a selected configuration directory. OpenCode reads those files natively; there is no distributed KSI `setup(ctx)`, `agent.transform`, or KSI entry in `plugins`. [OpenCode agents](https://opencode.ai/v2/docs/agents) and [configuration](https://opencode.ai/v2/docs/config) define the runtime semantics.

OpenCode's Build and Plan and the installed Design are available as Primaries. OpenCode's Explore and the installed Developer, Test Runner, and Reviewer are Subagents. Build/Plan/Explore retain their built-in system prompts. Build may work directly or delegate as appropriate; the default Developer cannot delegate. `design-previews/` is an artifact convention, not an edit permission boundary. Official Superpowers and a goal plugin remain separate, user-owned installations.

Design is the normal owner of material product/visual/interaction design, using the real product and approved context, bounded Explore investigation for local facts or authorized external examples, rendered alternatives where direction is unresolved, and optional image-backed Reviewer feedback. Reviewer also handles code review when asked. Build remains suitable for small established-pattern UI edits and production integration. The opt-in skill kit supplies production and polish skills with local craft references; OpenCode does not automatically compose OpenDesign's craft or design-system metadata. This does not add an orchestrator role, a KSI preview runtime, a mandatory Design→Build path, or a model override. The project's own design sources and Human-approved preference evidence, not the packaged Neutral Modern reference, determine its visual identity. See [Design work](design.md).

Each installed custom role owns its description, mode, system prompt, and narrow native permissions. The bundle has no skill whitelist and omits model/variant/steps so existing user settings remain in their native configuration layer. The installer does not parse or rewrite JSONC and refuses differing file collisions without explicit replacement and backup. A collision in a *different* config layer still requires effective-config inspection; file checks alone do not settle OpenCode precedence. OpenCode's last matching permission rule wins, and its permissions are not an OS sandbox.

No slash command is installed. The former six `ksi_*` evidence tools, output archive, runtime delegation/signature checks, helper lifecycle guard, and continuity hooks are not part of the installer distribution. Agents can use normal authorized OpenCode tools and optional shared `AGENTS.md` guidance, but this is guidance, not the same enforcement or telemetry. The approved product milestone still needs Human end-to-end acceptance; package tests alone do not establish it.

OpenChamber is a client: managed mode uses its managed OpenCode server's configuration, external-server mode uses the external server's configuration. OpenChamber's orchestration tool is managed-only. Neither UI mode has been accepted from the local package checks.
