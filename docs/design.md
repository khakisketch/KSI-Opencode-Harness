# Design work in the native harness

Design is the normal Primary for material product, visual, and interaction design; the Human chooses its direction. Build can handle small UI changes within approved patterns and owns production integration and technical verification. Design is directly selectable, not a mandatory Build handoff stage. These are responsibilities, not a restriction on native agent delegation or installed skills.

## The quality loop for material design work

This is a set of capabilities to apply proportionally, not a required stage sequence. A small change using an approved pattern can go straight through Build. A new product direction benefits from the whole loop.

1. **Ground the brief in the real product.** Identify the person, task, decision, and failure cost. Inspect current screens, relevant states, semantic components, tokens, and existing design sources. Separate observations from assumptions. Explore can gather bounded local facts or external examples if this is useful and authorized; request sources and dates for current external claims. For a reference, record what to keep, change, and not copy, and why it helps the user's job. The previous six-screen KSI Safety comparison used a textual demo brief rather than the live product's visual context; its apparent Design advantage was not Human acceptance of either candidate.
2. **Make the visual choice visible.** If direction is open, create materially different candidate treatments on the screen or flow that carries the core user task. Different layouts should express different information priorities or interaction ideas, not just palettes. Show the rendered candidates and concise tradeoffs; the Human chooses or revises. If a direction is already approved, do not manufacture variants.
3. **Craft and inspect the choice.** Work in the actual UI stack or a faithful, isolated prototype when practical. Reuse existing product patterns. `frontend-design` supports making or reshaping UI; `impeccable-design-polish` supports an inspected existing artifact; `web-design-guidelines` is a separate technical-review lens, not a taste engine. For material work, read the relevant bundled craft references from each skill's local `references/craft/` directory. OpenCode lists supporting files but does not load them automatically. Product sources prevail over generic numerical craft heuristics. Render with existing browser or preview tooling; no KSI-only preview application is required. Examine the states and widths that matter to the task, without a fixed screenshot quota.
4. **Critique against the job and the chosen direction.** Optionally ask Reviewer for design review with the artifact/version, task, direction, and actual image captures. Reviewer checks task clarity and states separately from composition and visual craft, names concrete regressions, and preserves what works. A read permission and a screenshot path do not prove visual inspection: the selected model must accept image input and actually receive the pixels. If that cannot be established, label visual critique unverified. Design revises as needed; Reviewer does not approve on the user's behalf.
5. **Retain only real preference evidence.** Link a chosen or rejected artifact to the Human's stated reason. The project's existing `DESIGN.md` can point to this evidence when genuinely useful; it must not become a duplicate token set or a collection of preferences the Human never expressed. [The optional project entrypoint](design-system-template.md) shows the shape. Handoff to Build with the actual artifact, intended task behavior, important states, decisions, open questions, and approval status. [The optional handoff example](../examples/design-handoff.md) is not a mandatory form.

Quality is judged by the Human's absolute satisfaction and whether the intended product task is clearer, not merely by Design beating Build in a paired comparison. A native role prompt, three skills, craft references, and passing catalog tests cannot establish Claude Design-level output. Model vision capability, project evidence, rendered iteration, and Human feedback are separate conditions to verify in a real pilot.

Parallel read-only investigation or independent critique is useful when tasks are separable. Concurrent writers must own separate artifacts or worktrees; Design remains accountable for its resulting artifact. Reviewer's advice is not Human approval or production acceptance.

## Tools and boundaries

Use the project's own rendering and browser workflow first. [The Playwright MCP example](../examples/design.project.jsonc) is optional and is not installed by this harness. Mobbin or other references may inform a direction, but they are not a prerequisite. Image generation can help explore a direction; it cannot substitute for inspecting a real UI.

KSI vendors a pinned subset of OpenDesign components. `--with-design-kit` installs only `frontend-design`, `impeccable-design-polish`, and `web-design-guidelines` as native OpenCode skills, with six distinct craft references distributed beside the first two. Skills are available to relevant roles without a KSI skill allowlist; the role suggestions are not access restrictions. `design-brief`'s fixed palette/defaults and `reference-design-contract`'s mandatory files are not imposed on projects. OpenDesign's `design-review` is a catalog pointer, not a complete skill; `brand-extract` and its browser skill expect OpenDesign-specific context. Use the project's existing browser or Playwright workflow instead. The packaged Neutral Modern system is a separate opt-in reference, not an installed default or a project design system. Do not copy its colors, tokens, components, or layout rules into an established product merely because it is available; the project owner chooses whether it fits. Provenance and licenses are in [`vendor/open-design/UPSTREAM.md`](../vendor/open-design/UPSTREAM.md).

Do not claim a visual check, approval, or completed integration that has not occurred. Build can return fidelity questions to Design. Human acceptance remains separate from Build's technical checks.
