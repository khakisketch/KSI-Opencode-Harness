# 프로젝트 지식과 상태 관리

전역 하네스는 **지식을 찾고 유지하는 원칙**을 제공하고, 제품 내용과 정본의 권위는
각 프로젝트가 소유합니다. 별도 프레임워크·초기화 명령·필수 문서 세트는 없습니다.

## 전역과 프로젝트의 책임

| 위치 / 책임 | 담는 내용 | 담지 않는 내용 |
| --- | --- | --- |
| 전역 `AGENTS.md` | 관련 정본 선택, 실제 상태 대조, 변경된 사실 갱신의 공통 원칙 | 개별 제품의 범위·경로·로드맵, 상세 문서 양식 |
| 프로젝트 `AGENTS.md` | 짧은 제품 소개, 주제별 현행 정본 위치·충돌 시 권위, 실행·검증 진입점, 프로젝트 고유 경계 | 전역 원칙 사본, 전체 PRD, 누적 작업 일지 |
| 현행 제품·경험·시스템 정본 | 현재 승인된 목적·업무·책임·계약 | 구현됐다는 추정, 미승인 제안을 확정 사항으로 표현 |
| 제품 상태 원장 | 실제 구현, 검증 범위·근거, 남은 문제, 승인된 작업 연결 | 매 도구 호출·세션별 일지, 독자적인 새 목표·승인 |
| 결정·검증 이력 | 이유, 대안, 당시 결과와 환경·버전 | 현행 정본을 매번 대신 해석해야 하는 누적 덧붙임 |
| 세션 체크포인트 | 진행 중인 특정 과업의 재개 위치·작업 파일·다음 조치 | 제품 전체의 상태·우선순위를 새로 확정 |

표의 각 행은 **문서 책임**이지 만들어야 할 파일이 아닙니다. 기존 문서의 한 절이
여러 책임을 맡아도 됩니다. 시스템·계약·ADR이 이미 있으면 그대로 연결합니다.
프로젝트들의 제품 상태를 전역 공용 원장에 모으거나 프로젝트 파일을 일괄 생성하지 않습니다.

## 현행 정본에서 찾을 네 가지 관점

| 관점 | 답해야 할 질문 |
| --- | --- |
| 제품 | 누구의 어떤 문제를 풀며, 현재 범위와 제외 범위는 무엇인가? |
| 경험 | 사용자가 어떤 상황에서 어떻게 업무를 끝내며, 각 화면은 무엇을 책임지는가? |
| 시스템 | 어떤 컴포넌트가 데이터·상태를 소유하고, 어디서 연결·저장·전달되는가? |
| 상태 | 실제로 어디까지 구현·검증됐고, 중요한 미확인·차단 사항은 무엇인가? |

`PRODUCT.md`·`EXPERIENCE.md`·`SYSTEM.md`·`STATE.md`는 가능한 이름일 뿐입니다.
작으면 제품·경험을 합치고, 독립적으로 관리할 필요가 생길 때만 나눕니다. 같은 역할의
정본이 있는데 요약본을 새 권위로 만들지 않습니다. 요약을 두더라도 원소유 정본을
연결하고, 충돌은 기존 권위에 따라 해결하며 승인된 계약을 임의로 약화하지 않습니다.

### 경험 관점의 최소 내용

경험 정본은 디자인 토큰 모음이 아니라 **업무와 화면 책임의 기준**입니다.
관련 업무를 이해하는 데 필요한 사용자·환경, 목표·완료 상태, 앞뒤 흐름, 화면별
주요 정보·행동·우선순위와 중요한 실패·복구 상태를 설명합니다. 기존 계약·확정 시안·
실제 화면이 있으면 연결하고, 고정되지 않은 배치·비율은 구현 담당자가 판단합니다.

문서에 목적이 적혀 있다는 것만으로 UI가 적합해지는 것은 아닙니다. 실제 대상 환경의
렌더·조작·핵심 상태를 원래 사용자 과업과 대조해야 합니다.

## 읽기는 과업에 맞춰 선택

프로젝트 `AGENTS.md`는 지도이며 읽기 순서를 강제하는 목록이 아닙니다.
화면 과업은 해당 업무·화면 책임, 데이터 변경은 소유 경계·관련 계약, 작업 재개는
해당 상태·체크포인트와 실제 변경처럼 **현재 판단에 필요한 근거**를 골라 봅니다.
작은 수정에 전체 제품 문서 열람을 붙이지 않고, 연결된 사실이 불분명하면 범위를 넓힙니다.

문서가 구현을 증명하지는 않습니다. 재개·분해·통합에 영향을 주는 상태는 관련 코드,
미커밋 변경, 최근 커밋과 실행 증거를 대조합니다. 반대로 코드가 다르다고 승인된
제품 요구사항을 구현에 맞춰 바꾸지도 않습니다. 없는 내용은 미확인·제안으로 구분합니다.

프로젝트 기억(예: ai-memory)은 이전 결정·실패·남은 작업을 찾는 **보조 자료**입니다.
기억에 적힌 내용은 현재 제품 정본이나 사용자 지시를 대신하지 않으며, 현재 코드·실행
결과와 대조해 유효성을 확인합니다. 기억의 수집·보존 정책은 해당 프로젝트와 기억
도구의 설정을 따릅니다.

OpenCode V2의 `AGENTS.md` 자동 로딩과 일반 문서 참조는 별개입니다. 이 구조를 위해
제품 문서 전체를 전역 `instructions`에 추가하지 않습니다. 상세 안내인 이 문서 역시
매 세션에 자동 주입하지 않습니다. [공식 지침 로딩 설명](https://opencode.ai/v2/docs/instructions).

## 제품 상태 원장은 현재 사실만 빠르게

기존 원장의 현행 요약을 먼저 정리합니다. 다음은 필요한 정보를 고르는 예시이며,
고정 열·상태 enum·검사 양식은 아닙니다.

```markdown
# 제품 상태
기준: <확인 시점 · 관련 코드/빌드/환경 · 미커밋 변경 영향>

| 기능 / 업무 흐름 | 실제 구현 | 검증 근거와 한계 | 남은 문제 |
| --- | --- | --- | --- |
| <업무> | <연결된 코드·구현 범위> | <테스트·실행·렌더 근거, 미확인 범위> | <차단·미완료> |

현재 승인된 작업: <기존 과업/계획의 해당 절 링크>
결정·이력·상세 검증: <기존 기록 링크>
```

프로젝트의 기존 상태 어휘·인수 체계를 유지하고 **구현·검증·사용자 인수**를 섞지
않습니다. 예를 들어 호스트 테스트 통과는 실기 검증이 아니고, 모의 화면은 고객
수용이 아닙니다. 제품 slice와 배정된 단기 과업도 서로 대신하지 않습니다.

오래된 상세 기록은 이력으로 분리하거나 기존 기록을 연결합니다. 현행 요약에 결론을
반영해 새 담당자가 긴 수정 이력에서 최신 결론을 추리하지 않게 하며, 당시 근거를
잃거나 과거 결과를 새 검증처럼 고쳐 쓰지 않습니다. 오류 정정은 정정임을 남깁니다.

## 누가 언제 갱신하는가

- 실행 담당자는 승인된 범위 안에서 변경된 사실과 근거를 반환하고, 자신이 소유한
  현행 문서를 함께 갱신합니다. 공유 원장·정본은 한 명이 소유하고 Build가 통합합니다.
- 승인된 제품 결정, 지속되는 구현 상태, 검증 결과나 중요한 차단 사항이 바뀌면
  해당 정본과 상태 요약을 맞춥니다. 단순 정리처럼 제품 사실이 바뀌지 않는 수정은
  원장에 매번 새 행을 추가하지 않습니다.
- 분석·자문만 맡았다면 제안과 근거를 반환합니다. 문서 관리라는 이유로 구현하거나
  제품 정본·원장을 임의 변경하지 않으며, Plan은 구현 승인 단계가 아닙니다.
- 결정 기록에는 이유를, 현행 정본에는 현재 유효한 결론을 남깁니다. 작업 재개용
  체크포인트는 승인된 과업을 가리키고 별도의 다음 제품 목표를 만들지 않습니다.

기존 프로젝트에 적용할 때는 먼저 현재 지도를 재사용하고, 이번 승인 과업에서 필요한
공백만 보완합니다. 문서 이전·이력 분리·권위 변경은 그 작업 범위 안에서 수행하며,
전역 설치가 다른 프로젝트의 파일을 자동으로 재구성하지 않습니다.

선택적으로 참고할 [프로젝트 진입점 예시](../examples/project-AGENTS.md)가 있습니다.
설치·링크·fixture 검사는 지침 전달을 확인할 뿐, 실제 모델의 이해나 제품 품질 향상을
증명하지 않습니다. 효과는 실제 제품 과업의 결과로 확인합니다.
