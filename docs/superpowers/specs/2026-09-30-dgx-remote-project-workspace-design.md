# DGX 원격 프로젝트 폴더 작업 — 설계

Date: 2026-09-30
Status: revised spec and native execution plan approved; Labs gateway deployed; workspace implementation partial, custom-image rollout paused on pre-change daemon test failures

## 1. 목적과 합의된 범위

어느 기기에서 브라우저로 접속하든 DGX 서버의 프로젝트 폴더를 선택하고, 그 폴더의 실제 파일을
작업 대상으로 사용한다. 접속 기기의 파일 선택기나 단순 참고 폴더 첨부로 대체하지 않는다.

- 탐색 범위: DGX의 `/home/ksi` 전체 하위 디렉터리. 기본 시작 화면은 홈이며 Desktop 바로가기를 제공한다.
- 사용자가 프로젝트 폴더를 선택하고 `열기`를 누르면 그 폴더의 읽기·쓰기 연결을 요청한 것으로 처리한다.
  프로젝트별 사전 승인 목록, KSI-CCTV 전용 제한, 별도 관리자 승인 절차는 없다.
- 홈 탐색은 디렉터리 목록 열람이다. 홈 전체 파일 내용을 모델에 전달하거나 홈 전체를 writable 연결하지 않는다.
- 첫 검증 대상은 `/home/ksi/Desktop/KSI-Projects/KSI-CCTV`이며, 이후 다른 홈 하위 프로젝트도 같은 흐름으로 연다.
- 홈 자체는 탐색 루트이지 프로젝트 작업 루트가 아니다. 실제 실행/저장은 선택한 하위 프로젝트를 기준으로 한다.
- 기존 KSI-CCTV 제품 코드와 운영 설정은 초기 연결 검증에서 수정하지 않는다.
- 이는 별도로 설치된 디자인 작업 공간의 원격 운영 개선이다. KSI npm 설치기의 범위를 넓히지 않는다.

## 2. 확인된 문제

실제 설치된 서버의 폴더 선택 경로는 Linux에서 native `zenity`를 실행한다. 현재 컨테이너에는
해당 실행 파일과 데스크톱 display 연결이 없으며, 요청은 500과 `zenity is not installed`를 반환한다.
또한 DGX 프로젝트 경로가 컨테이너에 연결돼 있지 않다. UID 정렬이나 GUI 패키지 설치만으로는
원격 브라우저에서 서버 폴더를 선택하는 요구를 해결하지 못한다.

기존 코드에는 서로 다른 두 기능이 있다.

- 작업 디렉터리/linkedDirs 첨부: 에이전트에게 참고 폴더를 알려주는 기능.
- 기존 폴더 프로젝트 열기: `/api/import/folder`가 canonical `metadata.baseDir`를 실제 프로젝트 루트로 설정.

두 번째 기능을 재사용한다. 일반 프로젝트 생성/metadata 수정으로 baseDir 보호를 우회하지 않는다.
실제 실행 이미지와 소스 checkout의 버전 표시가 다르므로 구현 전 빌드 산출물의 대응 리비전을 확인한다.

## 3. 대안과 선택

1. **선택: 홈 탐색 + 선택 기반 자동 작업 루트 연결.** 사용자가 폴더를 고르는 일반 개발 도구처럼
   동작한다. 기존 folder import를 재사용하고, host 연결 서비스가 선택한 프로젝트의 연결을 처리한다.
2. **제외: 프로젝트별 고정 승인 목록.** 초기 smoke test에는 간단하지만 프로젝트를 바꿀 때마다
   운영자가 설정해야 하므로 이번 사용성 요구에 맞지 않는다.
3. **제외: 홈 전체 writable 마운트.** 연결은 간단하지만 폴더 탐색을 홈 전체 쓰기 권한으로 확대한다.
   사용자가 설명한 탐색/실제 작업의 구분에 맞지 않는다. native GUI 공유도 원격 웹 선택을 대체하지 못한다.

## 4. 구성과 데이터 흐름

```text
원격 브라우저
  → 기존 인증/동일 출처 검사
  → daemon의 원격 폴더 목록 프록시
  → DGX host의 목록 API (홈 하위 디렉터리 이름만)
  → 사용자가 프로젝트 폴더 선택/열기
  → host 연결 서비스가 선택한 프로젝트 경로를 자동 연결
  → 기존 folder-import 경로 (기존 workspace 권한 검사 유지)
  → canonical 외부 프로젝트 루트
  → 실제 DGX 파일에 읽기/쓰기 및 미리보기
```

### Host 탐색과 연결 서비스

- 서비스는 DGX loopback에만 노출하고 daemon과의 호출을 별도 인증한다. 토큰은 문서/소스/Git에 저장하지 않는다.
- 목록 API는 디렉터리 목록과 경로 상태만 반환한다. 파일 내용, 임의 명령, 마운트 변경 기능을 겸하지 않는다.
- 서버가 정한 홈 루트와 상대 경로를 사용한다. 직접 경로 입력도 같은 canonical 경로 검사에 통과하면 허용한다.
- 숨김 폴더는 기본 숨김/표시 토글을 제공한다. 심볼릭 링크는 canonical 대상이 홈 안이면 탐색 가능하며
  홈 밖이면 연결할 수 없는 이유를 표시한다. 일괄적인 숨김/링크 차단으로 프로젝트를 찾지 못하게 하지 않는다.
- 응답은 이름, 상대 경로, 탐색 가능 여부, 선택 가능 여부와 불가 사유로 제한한다. 홈에서 부모 이동은 비활성화한다.
- 연결 API는 인증된 `열기` 요청의 canonical 프로젝트 경로만 받는다. 서버 설정에 고정된 디자인 컨테이너의
  bind mount만 관리하며, 임의 컨테이너/명령/host 경로/이미지를 클라이언트가 지정할 수 없다.
- host 연결 서비스는 Docker 관리 권한을 필요로 하는 별도 신뢰 컴포넌트다. 이 권한을 에이전트나
  컨테이너에 전달하지 않으며, 입력 검증과 인증 실패 테스트를 배포 전 필수로 한다.
- 도우미가 실패하면 브라우저에 원인과 재시도 안내를 표시한다. 접속 기기 선택기로 자동 대체하지 않는다.

### 선택 기반 연결과 컨테이너

- 인증된 사용자의 `열기`가 연결 의사 표시다. 서버는 존재하는 디렉터리인지, 홈의 하위 경로인지 확인하고
  host와 container에 같은 절대경로로 writable 연결한다. 일반 folder import의 workspace 권한 검사는 유지한다.
- 직접 import/작업 루트 교체 요청에도 같은 홈 경계와 연결 상태 검사를 적용한다. UI만 검사하지 않는다.
- 홈 루트 자체와 SSH/인증 저장소 등 자격증명 전용 디렉터리는 프로젝트 선택 대상이 아니다.
- Desktop 전체, 홈 전체, Docker socket을 에이전트 컨테이너에 추가 마운트하지 않는다.
- 연결 상태는 host 서비스가 관리한다. 이미 연결된 프로젝트는 바로 열고, 새 bind mount가 필요하면
  서비스가 기존 설정을 보존한 채 컨테이너를 재생성한다. 사용자가 compose를 직접 편집하지 않는다.
- 실행 중인 생성 작업이 있으면 자동 재생성하지 않고 완료 후 다시 열도록 안내한다. 연결 중 상태를
  표시하고 health 회복 후 import를 이어간다. 실패하면 기존 구성으로 복구하고 연결 실패를 표시한다.
- 연결한 프로젝트들은 이후 다시 열 수 있도록 유지한다. 공유 컨테이너의 에이전트는 이미 연결된
  다른 프로젝트에도 OS 수준 접근이 가능하다. 선택한 cwd를 프로젝트별 sandbox라고 설명하지 않는다.
- 기존 credential mounts와 host networking은 별도의 알려진 신뢰 경계다. 이 변경을 완전한 OS sandbox로 설명하지 않는다.
- 프로젝트 안의 `.env` 등 비밀정보도 자동 읽기/모델 전달 대상이 아니다. UI/API의 민감 경로 차단과
  기존 credential 노출 경계를 구현 계획에 명시하고, 전체 프로젝트 마운트만으로 비밀정보 격리를 주장하지 않는다.

### 웹 UI와 기존 import

- headless/remote 모드에서는 브라우저 내부의 서버 폴더 목록을 사용하고 `DGX 서버 폴더`라는 위치를 표시한다.
- 홈/ Desktop 바로가기, breadcrumb, 부모 이동, 직접 경로 입력, 숨김 폴더 토글을 제공한다.
  `추가 승인 필요` 버튼 대신 선택 → 연결 상태 → 프로젝트 열기로 이어지는 단일 흐름을 제공한다.
- 선택한 루트와 실제 쓰기 대상 경로를 열기 전에 명시한다. 기존 파일에 영향을 줄 수 있음을 알린다.
- 폴더 프로젝트 열기에는 기존 import의 workspace 권한/경로 검사/entry 감지를 사용한다.
- 파일 읽기/쓰기도 canonical 작업 루트 밖을 가리키는 symlink를 거부해야 한다. 에이전트 실행의
  cwd/산출물 루트가 이 폴더와 일치하는지도 확인하며, UI 저장 성공만으로 생성 실행까지 검증됐다고 주장하지 않는다.
- 기존 관리형 디자인 프로젝트의 저장 루트를 조용히 바꾸거나 산출물을 자동 이동하지 않는다.
- 참고 폴더 첨부 UI에 같은 목록을 사용하더라도 그 기능은 참고용으로 유지한다. 실제 작업에는
  `프로젝트 폴더 열기` 흐름을 사용한다.
- 기존 로컬 데스크톱 모드의 native picker는 유지한다. 원격 모드에서만 명확한 분기를 사용한다.

## 5. 기존 파일 보호와 배포

- KSI-CCTV 현재 baseline은 `master`, `a89ef2d`, tracked worktree clean으로 관찰했다. 실행 시 다시 확인한다.
- `.env`, 카메라/운영 설정, 데이터, 모델, Git 내부 파일은 초기 테스트에서 읽거나 변경하지 않는다.
- 연결 검증용 파일만 `design-previews/remote-workspace-smoke/` 아래 새 이름으로 생성한다.
- 동명 파일이 있으면 거부한다. 실제 제품 화면 생성/수정은 별도의 사용자 요청에서 수행한다.
- rollback은 기존 compose 설정/이미지 복구와 이번 변경에서 생성한 파일만 대상으로 한다.
- 기존 upstream checkout의 compose 변경은 사용자 작업으로 보존한다. 별도 작업 공간에서 구현/빌드하고
  재현 가능한 source-only 통합 자산으로 기록한다. 게시된 npm beta와 태그는 변경하지 않는다.
- container 재생성 및 서비스 추가는 승인된 구현 계획/배포 범위에 따라 수행하고, 진행 중인 디자인 작업을 확인한다.

## 6. 검증과 사용자 acceptance

자동/통합 검증:

1. 인증 없는 목록 요청, 다른 origin, 상위 이탈, 절대경로 주입, symlink 이탈이 거부된다.
2. 홈/ Desktop/다른 홈 하위 프로젝트를 탐색·선택할 수 있고, 고정 승인 목록 없이 연결된다.
   직접 경로 입력과 홈 내부 symlink는 정상 동작하고, 홈 밖 경로와 자격증명 저장소 선택은 거부된다.
3. KSI-CCTV 및 별도 임시 fixture 프로젝트의 import가 canonical 외부 루트를 유지한다.
   파일을 관리형 저장소로 복사하지 않는다. 임시 fixture 외 다른 제품 프로젝트를 테스트 목적으로 수정하지 않는다.
4. 지정 테스트 파일을 UI/API에서 작성하면 DGX의 같은 파일에 같은 bytes가 존재한다.
5. DGX에서 테스트 파일을 수정하면 디자인 작업 공간에서도 변경을 읽을 수 있다.
6. 컨테이너 재시작 뒤 프로젝트 경로 연결이 유지되고, MCP는 별도로 재확인한다.
7. 기존 tracked 파일, 운영 설정, provider 설정을 변경하지 않았음을 before/after 증거로 확인한다.
8. 새 프로젝트 연결 시 자동 재생성/health 대기/import 재개, 연결 실패 복구, 실행 중 작업 보호를 검증한다.
   연결 API에 임의 컨테이너/명령/홈 밖 경로를 주입해도 host 관리 동작이 일어나지 않아야 한다.

사용자 acceptance: 원격 브라우저에서 `홈 → Desktop → KSI-Projects → KSI-CCTV`를 열고,
테스트 파일을 저장/다시 읽어 DGX 원본 폴더에서 실제 작업된다고 확인한다. 이어 별도 홈 하위 fixture
프로젝트를 관리자 설정/추가 승인 없이 열 수 있는지 확인한다.

Cloud 상태/모델 오류, optional brand/font 파일, 협업 workspace context 문제는 별도 원인이다.
폴더 연결을 위해 Cloud CLI 설치나 가짜 브랜드 파일 생성을 하지 않는다.

## 7. 승인 단계

초기 Desktop/KSI-CCTV 전용 설계는 사용자 검토로 승인됐으나, 이후 사용자가 홈 탐색과 적극적인 연결을
요청해 이 문서를 수정했다. 이후 수정본과 구현 계획의 native 실행/서버 반영이 승인됐다.
계획: `../plans/2026-09-30-dgx-remote-workspace.md`. Labs 조회 gateway만 우선 배포했으며,
홈 폴더 연결은 원본 daemon 테스트 기준선 실패에 대한 처리 결정 전까지 배포하지 않았다.
