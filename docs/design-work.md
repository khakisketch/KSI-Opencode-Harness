# 디자인 작업 계약 (Design delivery)

디자인은 별도 에이전트나 승인 단계가 아니라, UI 과업의 완료 기준입니다. 이 문서는 Build·Plan·General이 같은 과업을 어떻게 이어서 완료하는지 정의합니다. 상시 주입되는 지침이 아니며, UI 과업을 맡을 때 읽습니다.

## 적용 범위

- 새 화면·사용자 흐름, 큰 UI 개편, 사용성 문제가 확인된 화면.
- "비평만" 요청은 findings에서 멈춥니다. 구현·렌더 검증은 별도 과업으로 명시합니다.
- 문구·수치 변경, 기존 컴포넌트 재사용, 이미 정해진 패턴의 적용은 바로 구현합니다.

## 역할

- **Build**: 목표·범위·통합·최종 검증. UI 판단의 최종 책임.
- **Plan**: 정보구조·방향·대안·위험 자문. 구현·승인 권한 없음.
- **General**: 범위가 정해진 UI 구현, 실제 렌더 검증, 같은 과업의 수정. 하위 에이전트 없음.
- **Explore**: 코드·레퍼런스 조사. 구현 없음.
- Design 에이전트는 두지 않습니다. 디자인 승인 게이트도 두지 않습니다.

## 완료 기준

1. **제품 과업 이해**: 사용자가 이 화면에서 무엇을 비교·판단·완료해야 하는가.
2. **방향 제안**: 기존 디자인 시스템, 레퍼런스, 대안을 비교하고 선택 이유를 남긴다.
3. **구현**: 실제 UI 코드와 인터랙션. 기존 기능·데이터 계약을 보존한다.
4. **실제 렌더 검증**: 실행 중인 제품에서 첫 화면, 주요 조작, loading/empty/error, 반응형을 확인한다.
5. **수정**: 발견한 문제를 같은 과업에서 수정하고 동일 사용자 작업으로 재검증한다.
6. **인계**: 변경 파일, 실행한 테스트/명령, 스크린샷·관찰, 남은 위험, 정본 후보를 Build에 넘긴다.

비평만으로 완료를 선언하지 않습니다. 렌더하지 못했으면 tested / simulated / unverified를 구분합니다.

## General에 넘길 작업 브리프

```text
목표: 사용자가 완료해야 하는 실제 과업.
현재 화면·흐름: 관련 파일과 현재 동작.
제약: 디자인 시스템, 데이터 계약, 권한, 보존할 기능.
산출물: 구현 diff, 실제 렌더 증거, 실행한 검증, 남은 위험.
완료 조건: 주요 조작과 loading/empty/error/반응형을 실제 제품에서 확인.
```

General은 결과를 Build에 돌려주고, Build가 통합·최종 수용을 결정합니다.

## be-ambitious (선택형)

`be-ambitious`는 더 높은 목표·전문가 방법·다분야 관점을 쓰게 하는 선택형 스킬입니다. 디자인 과업에서 강제하지 않습니다.

- 프로젝트의 `.opencode/skills/be-ambitious/SKILL.md`에만 설치하고, 전역에 배포하지 않는다.
- Build는 포괄적 목표나 품질 상향이 필요할 때 사용한다.
- Plan은 방향·대안·프롬프트 구체화까지만 사용하고 구현하지 않는다.
- General/Explore는 기본적으로 사용하지 않는다. 이미 정한 범위를 수행한다.
- **Better, not bigger**: 기능·범위·권한을 임의로 늘리지 않는다.
- 결과는 실제 제품, 테스트, 렌더 화면, 사용자 과업 같은 외부 심판으로 확인한다.
- 스킬 사용 자체를 완료 근거로 삼지 않는다.

## 정본과 상태

- 채택된 UX 구조·디자인 규칙은 제품 정본에 기록한다.
- 진행 상태·의존성·재개는 Beads에 둔다.
- 세션 요약과 스킬 출력은 정본이 아니다.
- 별도 디자인 메모리나 결과 기록 시스템을 추가하지 않는다.
