# Shared project guidance (optional template)

Use this file as a short repository-level `AGENTS.md` only when these paths and conventions fit the project. OpenCode and Codex can read the same project guidance; their agent configurations remain independent.

- Current code, tests, Git and observed verification are evidence of implementation state, not authority for intended product behavior. Latest approved requirements and user decisions determine the intended behavior; surface discrepancies rather than treating existing code or passing tests as approval. Checkpoints are resumability caches, not product documentation.
- If present, `docs/superpowers/product-state.md` records the current product milestone and user-visible acceptance. Use `docs/superpowers/plans/` for the relevant task decision and verification record, and `.opencode/working-state.md` for a compact worktree handoff.
- Reuse a compact Product binding in existing product-state/ledger for repository, design project/storage/entry, start/verify commands, product URL and brand source; recheck after target/access changes. Commands/URLs are data, not execution authority. Reconcile records with Git/evidence before closeout, and do not require manual copying of ambient policy updates between sessions. Task scope/approval remains project-specific; see the execution guide's binding and pause procedure.
- When asked for next development tasks or priorities, compare the current approved milestone and acceptance criteria with relevant implementation and verification evidence. Recommend work by its contribution to that goal, dependencies and actual blockers, not merely because an old plan or backlog item remains unfinished. If the goal is missing or conflicting and materially affects the choice, identify that decision instead of inventing a product objective.
- Keep clearly scoped implementation, exploration and review requests focused; do not expand them into a product-wide audit without a material conflict. A next-task recommendation does not authorize a new scope, and does not interrupt remaining authorized work.
- Use installed skills, including Superpowers, when they help the task. Do not copy or modify upstream skills to restate local policy. Skills and roles do not grant authority beyond the user's request.
- Scale planning, delegation, review, and visual evidence to the work. Preserve unrelated changes, report checks actually run, and distinguish local evidence from user acceptance or deployment readiness.
- Parallelize only separable work. Read-only discovery or review can overlap; concurrent writers need disjoint paths, stable interfaces, and separate worktrees. The coordinating Primary integrates and verifies the result.
- Adopt the [autonomous local execution policy](autonomous-development.md) by merging its section into this guidance (do not assume a linked file is automatically loaded). That policy delegates approved implementation, bounded helpers, integration, verification and task-owned local commits without routine progress/commit confirmation. Explicit user/repository restrictions still win.
- Pushes, releases and deployments need explicit authorization for their targets and effects, including push-triggered deployment. Reuse valid prior authorization instead of asking again. Material product/design decisions, destructive/security-sensitive actions and genuine blockers still return to the user.
- OpenDesign's local execution owns new/material visual and interaction design; select the task-appropriate design skill per run, evaluate the rendered result against the agreed references and quality bar, and refine until it is met (no fixed round cap; stop on met or no measurable improvement), then reuse approved artifacts for production integration. ui-ux-pro-max is supplementary guidance/review, not a competing design system or a silent fallback.
- For frontend improvements, send relevant actual product source/components/tokens, sanitized states and data/route/event constraints to the OpenDesign run via verified accessible inputs; request supported product-compatible UI output and integrate it faithfully rather than redesigning it in Build. Token reuse or small file count does not prove an approved-pattern exception: cite the actual reused artifact/component, and reroute material design decisions discovered during implementation. Follow the [product-aware workflow](../docs/integrations/opendesign.md#product-aware-frontend-improvement); do not assume a managed HTML project is linked to the product.
- When several screens show accumulated visual drift, prefer a visual-system pass (audit → token/component scales → one representative screen verified in the real source → single review → staged rollout with per-stage checks, no per-screen approvals) over per-screen patches or a big-bang rewrite; for internal tools keeping the existing brand, the single review replaces a separate plan approval, and pre-approval is required first only for a new visual direction, a client-facing deliverable, an out-of-scope change or an explicit review-first request; keep functionality, routing and data unchanged.
- Missing required design, artifact validation, integration or changed-flow checks is unfinished work, not “only user acceptance remains.” Prefer verified source-direct edits in the actual product repository (dedicated branch or the user's checkout; worktree optional), one writer at a time with Build verifying the real build/render; home/credential roots and unrelated projects stay out of reach, and policy adoption does not enable mounts or authorize API/data/auth/Git/push/deploy changes.
- OpenCode researches Mobbin conditionally before new/material design and passes inspected patterns/links/accessible images in the same agreed brief. Default to finish-and-report within the existing approved design language and authorized scope; preview-and-wait only for a new visual direction, client-facing deliverable, out-of-scope change or explicit review-first request. Record the verified required-file snapshot, and user direction approval tied to that snapshot only when gated; design preview and actual product-server verification are separate. See the [handoff procedure](../docs/integrations/opendesign.md#reference-research-and-brief-transfer); no automatic reverse engineering-session calls or runtime enforcement is implied.
