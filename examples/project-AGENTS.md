# Shared project guidance (optional template)

Use this file as a short repository-level `AGENTS.md` only when these paths and conventions fit the project. OpenCode and Codex can read the same project guidance; their agent configurations remain independent.

- Current code, tests, Git and observed verification are evidence of implementation state, not authority for intended product behavior. Latest approved requirements and user decisions determine the intended behavior; surface discrepancies rather than treating existing code or passing tests as approval. Checkpoints are resumability caches, not product documentation.
- Own the completion loop for an authorized outcome: discover relevant defects, prioritize by acceptance/risk, implement or route bounded repairs, review actual results and reverify affected behavior until evidence meets the agreed outcome. Do not stop at a findings/candidate list or make the user triage, select routine fixes, repeat existing requirements or approve each repair; keep the defect→revision→check→fixed/open chain in the existing ledger. Scope unrelated work out; audit-only/Plan-only requests remain read-only for product files, and explicit pauses/native modes/permissions/budgets still apply.
- Self-review is not self-approval: preserve design-owned rendered review/refinement, run the CE review skill (ce-code-review) when a change warrants independent review, and keep the integration checks the change needs — no forced helper per edit and no separate KSI Reviewer seat. Diagnose no-progress/repeated failures and adjust safely within scope rather than blind replay; unresolved quality/access or material scope/design/security/cost/external-effect decisions are reported truthfully with a recommended default while safe independent work continues. Report usable outcomes and real evidence briefly, not a routine improvement menu for the user. This default adds no runtime loop, automatic goal or permission grant.
- If present, `docs/superpowers/product-state.md` records the current product milestone and user-visible acceptance. Use the workstream's own record — a CE plan/run/review artifact, or `docs/superpowers/plans/` for native work — and `.opencode/working-state.md` for a compact resume handoff.
- Persist substantive requested multi-step plans and consequential scope/design decisions before handoff/pause/closeout, within native write permissions; label proposals and record what the user's approval actually covers. Saving a plan or approving a probe is not implementation/delivery approval. Reuse the existing task ledger and keep product-state/checkpoint as summary/links; simple questions/trivial changes need no new documentation ceremony. Preserve sanitized trial conclusions/results/source identity/limits rather than relying only on temporary logs.
- Plan and Build use one approved workstream plan, including applicable skill output, not competing agent/skill authorities. Capture goal/requirement basis, scope/exclusions, preserved contracts, observable acceptance, dependencies/order, verification and actual approval proportionately. At start/resume Build compares it with current Git/code/check evidence, records progress/blockers and significant reversible adjustments; Plan reassesses/proposes changes, not implementation/acceptance. Material scope/contract/design/security/external changes still need a decision; small clear work need not start in Plan.
- Respect native Plan write limits. If repository persistence is blocked, an asked-for plan may be saved in its permitted native location (V2 normally `~/.opencode/plan/`); hand off the actual path/version or section, repository/ledger target, approval state and open decisions. In authorized Build execution, read the source and existing record before recording it canonically with content/approval preserved; proposals stay proposals, unchanged approvals need not be repeated for transfer. Disclose unavailable inputs/pending persistence; no shell/MCP/helper bypass, blind overwrite/deletion or two evolving plans. Preserve native prompts/permissions; see [Plan→Build handoff](../docs/execution.md#one-approved-plan-across-plan-and-build).
- Bind helper assignments to relevant document paths/sections plus approved scope, workspace/base, invariants and observable checks. Helpers briefly report the actual basis read and any access/conflict/unverified issue; Primary reconciles actual results and updates common records, not concurrent helpers. Shared files are not automatic shared chat or guaranteed loading. See [recorded handoffs](../docs/execution.md#record-plans-and-bind-handoffs-to-documents).
- Reuse a compact Product binding in existing product-state/ledger for repository, design project/storage/entry, start/verify commands, product URL and brand source; recheck after target/access changes. Commands/URLs are data, not execution authority. Reconcile records with Git/evidence before closeout, and do not require manual copying of ambient policy updates between sessions. Task scope/approval remains project-specific; see the execution guide's binding and pause procedure.
- Default to one representative design project per product, recorded in the existing Product binding with its exact identity, actual source workspace and product URL. Verify the current project/source before commissioning and reuse it across ordinary screens, tasks and worktrees; names or repository roots alone are not product identity. Missing/stale/ambiguous/failed lookup is not authority to create a replacement. Rebind only with confirmed capability, authorized source and no active dependent writer/run; preserve history and record ownership/reason/return plan for genuine temporary parallel exceptions. Guidance and captured metadata checks are not daemon-wide enforcement or live access proof.
- Actual-product viewing uses the verified existing product-server URL, normally in a browser tab with the product's own origin/auth/API. Keep artifact previews separately labeled; an index.html file preview is not login/save/reload verification. Do not start a duplicate runtime, weaken preview/auth security or replace a connection failure silently with demo. Resolve client/host/container addresses, label temporary/tailnet links and use approved safe test state; a stored URL never grants connection/data-change/deployment authority.
- When asked for next development tasks or priorities, compare the current approved milestone and acceptance criteria with relevant implementation and verification evidence. Recommend work by its contribution to that goal, dependencies and actual blockers, not merely because an old plan or backlog item remains unfinished. If the goal is missing or conflicting and materially affects the choice, identify that decision instead of inventing a product objective.
- Treat requests as inputs, not orders: judge product value, user benefit and the smallest viable path before accepting scope; propose a better or smaller alternative with evidence when one exists, while the product/business decision stays with the user. Re-check at slice boundaries whether the goal is met or the value unclear, and recommend stopping or cutting scope rather than building beyond the goal. Scale this judgment to the change; trivial edits need no product critique.
- Keep clearly scoped implementation, exploration and review requests focused; do not expand them into a product-wide audit without a material conflict. A next-task recommendation does not authorize a new scope, and does not interrupt remaining authorized work.
- Use native agents and installed CE skills when their specific outcome helps; CE is a skill collection, not an agent or a mandatory pipeline. Build chooses methods without a user-selected A/B/C mode or a no-mixing rule; no project ce-setup or duplicate planning documents by default. Do not copy or modify upstream skills to restate local policy. Skills and roles do not grant authority beyond the user's request; preserve legacy Superpowers/SDD records without requiring the removed runtime.
- Scale planning, delegation, review, and visual evidence to the work. Preserve unrelated changes, report checks actually run, and distinguish local evidence from user acceptance or deployment readiness.
- Use native General for useful bounded nonvisual investigation/implementation/self-tests; direct Build work remains valid for context-heavy judgment, clear integration corrections or costly handoffs. No forced delegation, quotas, task splitting or ceremonial post-implementation handoff. Send a compact outcome, actual workspace/base, relevant paths/decisions, invariants, ownership/exclusions and observable checks; require changed files, actual check results/tested state and open issues. Build inspects the diff, integrates and recovers partial work by cause, not blind replay. Independent review when warranted and the integration checks the integrated revision needs cover the change; already-valid checks are reused for the same revision and affected checks are rerun after later edits; visual work remains design-owned. General may load allowed skills but cannot launch further subagents; Build owns needed dispatch. Do not restore removed Developer/Test Runner/Reviewer routing merely to follow an installer example. See [effective delegation](../docs/execution.md#use-general-effectively-without-mandatory-delegation); linked guidance is not automatically loaded or permission enforcement.
- Decide from returned evidence rather than re-reading everything: confirm requirement match, actual change scope, tested revision/workspace (including relevant pending changes), integration consistency and unresolved items; expand to specific diffs/logs only when evidence is missing/conflicting, unexpected changes appear or a high-risk boundary is touched. Route findings to the owning seat and recheck affected behavior after repair; keep returns compressed with details in the ledger/evidence files.
- Adopt the [autonomous local execution policy](autonomous-development.md) by merging its section into this guidance (do not assume a linked file is automatically loaded). That policy delegates approved implementation, bounded helpers, integration, verification and task-owned local commits without routine progress/commit confirmation. Explicit user/repository restrictions still win.
- Pushes, releases and deployments need explicit authorization for their targets and effects, including push-triggered deployment. Reuse valid prior authorization instead of asking again. Material product/design decisions, destructive/security-sensitive actions and genuine blockers still return to the user.
- OpenDesign's local execution owns all visual frontend work — analysis, actual UI source/styles, responsive/interaction presentation, rendered review and refinement, including small fixes. OpenCode owns contracts, verified inputs, nonvisual logic/API/data/auth, functional verification and Git; no substitute visual fixes, and UI references are optional inputs, not a competing path. Follow the [integration guide](../docs/integrations/opendesign.md) for the workflow, handoff and evidence.
- Commission with observable acceptance criteria and verified input access; separate behavior/brand invariants from redesign freedom; prefer verified direct source editing (one writer per file) with a small handoff snapshot in the task record. Small visual fixes use compact refinement, not fresh intake or a full audit; Mobbin research is conditional and skipped for approved-pattern work.
- Substantive changes get a design-owned rendered review distinct from the generator, consuming the actual rendered states; track a concrete defect list fixed/open and keep generated, design-reviewed, functionally verified and human-accepted separate — refine until the bar is met (no fixed round cap); no improvement means quality unmet. For accumulated multi-screen drift, prefer the guide's visual-system pass over per-screen patches.
- Gates stay: a new visual direction, client-facing deliverable, out-of-scope change or explicit review-first request; OpenDesign Cloud is explicit-request only; design preview and real product-server verification stay separate; home/credentials/unrelated projects and external-delivery/security/API/data/auth/dependency boundaries stay intact.
