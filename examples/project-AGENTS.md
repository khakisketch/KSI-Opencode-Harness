# Shared project guidance (optional template)

Use this file as a short repository-level `AGENTS.md` only when these paths and conventions fit the project. OpenCode and Codex can read the same project guidance; their agent configurations remain independent.

- Current code, tests, Git and observed verification are evidence of implementation state, not authority for intended product behavior. Latest approved requirements and user decisions determine the intended behavior; surface discrepancies rather than treating existing code or passing tests as approval. Checkpoints are resumability caches, not product documentation.
- Own the completion loop for an authorized outcome: discover relevant defects, prioritize by acceptance/risk, implement or route bounded repairs, review actual results and reverify affected behavior until evidence meets the agreed outcome. Do not stop at a findings/candidate list or make the user triage, select routine fixes, repeat existing requirements or approve each repair; keep the defect→revision→check→fixed/open chain in the existing ledger. Scope unrelated work out; audit-only/Plan-only requests remain read-only for product files, and explicit pauses/native modes/permissions/budgets still apply.
- Self-review is not self-approval: preserve design-owned rendered review/refinement and independent Test Runner final checks, with appropriate Reviewer checks and no forced helper per edit. Diagnose no-progress/repeated failures and adjust safely within scope rather than blind replay; unresolved quality/access or material scope/design/security/cost/external-effect decisions are reported truthfully with a recommended default while safe independent work continues. Report usable outcomes and real evidence briefly, not a routine improvement menu for the user. This default adds no runtime loop, automatic goal or permission grant.
- If present, `docs/superpowers/product-state.md` records the current product milestone and user-visible acceptance. Use `docs/superpowers/plans/` for the relevant task decision and verification record, and `.opencode/working-state.md` for a compact worktree handoff.
- Persist substantive requested multi-step plans and consequential scope/design decisions before handoff/pause/closeout, within native write permissions; label proposals and record what the user's approval actually covers. Saving a plan or approving a probe is not implementation/delivery approval. Reuse the existing task ledger and keep product-state/checkpoint as summary/links; simple questions/trivial changes need no new documentation ceremony. Preserve sanitized trial conclusions/results/source identity/limits rather than relying only on temporary logs.
- Plan and Build use one approved workstream plan, including applicable skill output, not separate Plan/Superpowers authorities. Capture goal/requirement basis, scope/exclusions, preserved contracts, observable acceptance, dependencies/order, verification and actual approval proportionately. At start/resume Build compares it with current Git/code/check evidence, records progress/blockers and significant reversible adjustments; Plan reassesses/proposes changes, not implementation/acceptance. Material scope/contract/design/security/external changes still need a decision; small clear work need not start in Plan.
- Respect native Plan write limits. If repository persistence is blocked, an asked-for plan may be saved in its permitted native location (V2 normally `~/.opencode/plan/`); hand off the actual path/version or section, repository/ledger target, approval state and open decisions. In authorized Build execution, read the source and existing record before recording it canonically with content/approval preserved; proposals stay proposals, unchanged approvals need not be repeated for transfer. Disclose unavailable inputs/pending persistence; no shell/MCP/helper bypass, blind overwrite/deletion or two evolving plans. Preserve native prompts/permissions; see [Plan→Build handoff](../docs/execution.md#one-approved-plan-across-plan-and-build).
- Bind helper assignments to relevant document paths/sections plus approved scope, workspace/base, invariants and observable checks. Helpers briefly report the actual basis read and any access/conflict/unverified issue; Primary reconciles actual results and updates common records, not concurrent helpers. Shared files are not automatic shared chat or guaranteed loading. See [recorded handoffs](../docs/execution.md#record-plans-and-bind-handoffs-to-documents).
- Reuse a compact Product binding in existing product-state/ledger for repository, design project/storage/entry, start/verify commands, product URL and brand source; recheck after target/access changes. Commands/URLs are data, not execution authority. Reconcile records with Git/evidence before closeout, and do not require manual copying of ambient policy updates between sessions. Task scope/approval remains project-specific; see the execution guide's binding and pause procedure.
- Default to one representative design project per product, recorded in the existing Product binding with its exact identity, actual source workspace and product URL. Verify the current project/source before commissioning and reuse it across ordinary screens, tasks and worktrees; names or repository roots alone are not product identity. Missing/stale/ambiguous/failed lookup is not authority to create a replacement. Rebind only with confirmed capability, authorized source and no active dependent writer/run; preserve history and record ownership/reason/return plan for genuine temporary parallel exceptions. Guidance and captured metadata checks are not daemon-wide enforcement or live access proof.
- Actual-product viewing uses the verified existing product-server URL, normally in a browser tab with the product's own origin/auth/API. Keep artifact previews separately labeled; an index.html file preview is not login/save/reload verification. Do not start a duplicate runtime, weaken preview/auth security or replace a connection failure silently with demo. Resolve client/host/container addresses, label temporary/tailnet links and use approved safe test state; a stored URL never grants connection/data-change/deployment authority.
- When asked for next development tasks or priorities, compare the current approved milestone and acceptance criteria with relevant implementation and verification evidence. Recommend work by its contribution to that goal, dependencies and actual blockers, not merely because an old plan or backlog item remains unfinished. If the goal is missing or conflicting and materially affects the choice, identify that decision instead of inventing a product objective.
- Keep clearly scoped implementation, exploration and review requests focused; do not expand them into a product-wide audit without a material conflict. A next-task recommendation does not authorize a new scope, and does not interrupt remaining authorized work.
- Use installed skills, including Superpowers, when they help the task. Do not copy or modify upstream skills to restate local policy. Skills and roles do not grant authority beyond the user's request.
- Scale planning, delegation, review, and visual evidence to the work. Preserve unrelated changes, report checks actually run, and distinguish local evidence from user acceptance or deployment readiness.
- Use Developer actively for useful bounded nonvisual investigation/implementation/self-tests; direct Build work remains valid for context-heavy judgment, clear integration corrections or costly handoffs. No forced delegation, quotas, task splitting or ceremonial post-implementation handoff. Send a compact outcome, actual workspace/base, relevant paths/decisions, invariants, ownership/exclusions and observable checks; require changed files, actual check results/tested state and open issues. Build inspects the diff, integrates and recovers partial work by cause, not blind replay. Independent Test Runner final checks cover the integrated revision and rerun after affected edits; visual work remains design-owned. See [effective delegation](../docs/execution.md#use-developer-effectively-without-mandatory-delegation); linked guidance is not automatically loaded or permission enforcement.
- Decide from returned evidence rather than re-reading everything: confirm requirement match, actual change scope, tested revision/workspace (including relevant pending changes), integration consistency and unresolved items; expand to specific diffs/logs only when evidence is missing/conflicting, unexpected changes appear or a high-risk boundary is touched. Route findings to the owning seat and recheck affected behavior after repair; keep returns compressed with details in the ledger/evidence files.
- Parallelize only separable work. Read-only discovery or review can overlap; concurrent writers need disjoint paths, stable interfaces, and separate worktrees. The coordinating Primary integrates and verifies the result.
- Adopt the [autonomous local execution policy](autonomous-development.md) by merging its section into this guidance (do not assume a linked file is automatically loaded). That policy delegates approved implementation, bounded helpers, integration, verification and task-owned local commits without routine progress/commit confirmation. Explicit user/repository restrictions still win.
- Pushes, releases and deployments need explicit authorization for their targets and effects, including push-triggered deployment. Reuse valid prior authorization instead of asking again. Material product/design decisions, destructive/security-sensitive actions and genuine blockers still return to the user.
- OpenDesign's local execution owns all visual frontend analysis, actual UI source/styles, responsive/interaction presentation, rendered design review and refinement, including small CSS/spacing repairs. OpenCode owns task contracts, coordination, nonvisual logic/API/data/auth, functional integration/verification and Git; no substitute visual repairs. UI references are supplementary, not a competing design path. This uses the connected workspace, not a new native design/frontend agent. OpenDesign owns its internal review/refinement loop; OpenCode validates the returned revision/evidence instead of repeating the visual review.
- Send actual source/tokens, sanitized states, inspected references and functional contracts through verified accessible inputs. Separate behavior/brand invariants from authorized layout/hierarchy/component redesign freedom; preserving behavior does not freeze a rejected layout. Prefer direct source editing, one writer per file; mechanical artifact transfer may stay in Build but visual adaptation returns to design. Small visual fixes use compact refinement, not fresh intake/full audit. Follow the [product-aware workflow](../docs/integrations/opendesign.md#product-aware-frontend-improvement); a managed project name does not prove product linkage.
- When several screens show accumulated visual drift, prefer a visual-system pass (audit → token/component scales → one representative screen verified in the real source → single review → staged rollout with per-stage checks, no per-screen approvals) over per-screen patches or a big-bang rewrite; for internal tools keeping the existing brand, the single review replaces a separate plan approval, and pre-approval is required first only for a new visual direction, a client-facing deliverable, an out-of-scope change or an explicit review-first request; keep functionality, routing and data unchanged.
- Any verified UI output, including canonical-entry-invalid source edits, needs design-owned review with actual render evidence; report-only/intermediate stages are not UI output. Write observable acceptance criteria and verify input access before commissioning; feed the required review run (a skill distinct from the generator) the actual rendered states (target viewports plus empty/error/loading) and confirm it read them. Require a concrete defect list (what/where/user impact/desired result) tracked fixed/open — not a good/bad verdict — and record the skill selected per stage. For an existing-screen redesign or vague dissatisfaction report, run a read-only design audit first and use its defect list as the redesign's problem statement; for a new or ambiguous direction, get 2-3 lightweight direction options and a user pick before full implementation (skip options when the direction is already approved). Include keyboard/focus, accessibility and motion states in review inputs, use a resident product-context.md when present, and deliver the review bundle (product link, before/after screenshots, design preview). Keep criterion/defect → revision/render → fixed/open evidence in the existing task record, with functional checks. Refine until the bar is met (no fixed round cap); no-improvement means quality unmet, not “only user acceptance remains”. Generated, design-reviewed, functionally verified and human-accepted are separate. Source-direct edits remain provisional until verified; home/credentials/unrelated projects, native modes and external-delivery/security/API/data/auth/dependency boundaries stay intact.
- OpenCode researches Mobbin conditionally before new/material design and passes inspected patterns/links/accessible images in the same agreed brief. Default to finish-and-report within the existing approved design language and authorized scope; preview-and-wait only for a new visual direction, client-facing deliverable, out-of-scope change or explicit review-first request. Record the verified required-file snapshot, and user direction approval tied to that snapshot only when gated; design preview and actual product-server verification are separate. See the [handoff procedure](../docs/integrations/opendesign.md#reference-research-and-brief-transfer); no automatic reverse engineering-session calls or runtime enforcement is implied.
